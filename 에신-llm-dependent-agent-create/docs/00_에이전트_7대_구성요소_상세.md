# 1.2 7대 구성요소(심화)

1.1 한눈에 보기에서 이름만 본 7대 구성요소(페르소나·LLM·목표·지식베이스·도구·안전 체계·자율 루프)를 하나씩 깊이 본다. 끝에는 이 구조를 통째로 기억하기 쉽게 양봉장에 빗댄 비유를 실었다.

### 🔧 심화 — 4자원(Model · Knowledge · Tools · Memory)으로 묶는 정리와의 매핑

위 7대 구성요소는 시스템 작동의 구성 요소를 세분화한 것이다. 한편 업계에서는 에이전트 런타임이 의지하는 핵심 요소를 **4대 자원(4-Resources)**으로 압축해 보기도 한다.

| 4자원 | 역할 및 정체 | 본 튜토리얼 7대 구성요소와의 관계 |
|---|---|---|
| **Model** | 추론과 의사결정을 수행하는 LLM 엔진 | = **LLM** |
| **Knowledge** / 지식·지침 | 판단의 기준이 되는 정적 지식 — 시스템 프롬프트·스킬·도메인 문서 | = **지식베이스** + **페르소나** |
| **Tools** | 현실 환경에 변화를 주는 실행 인터페이스 — API·MCP·코드 실행·검색 | = **도구** |
| **Memory** / 상태·기억 | 세션 간/스텝 간 맥락과 작업 이력을 보존하는 동적 상태 | 장기 = 지식베이스 **①직접 주입** · 단기 = **자율 루프**의 작업 상태 |

4자원 시각에서 **자율 루프**는 이 4대 자원을 엮어 굴리는 '엔진'이며, **목표**는 엔진에 입력되는 과업 명세이고, **안전 체계**는 자원 남용을 막는 가드레일이다.

## 1) 페르소나 — 누구로서 어떻게 일하는가

주로 **시스템 프롬프트(System Prompt)**를 통해 부여된다. 페르소나는 **이 에이전트가 무엇을 하는 존재인가**를 정한다 — 어떤 역할과 전문성으로, 무엇을 우선해 판단하고, 어떤 어투로 말하는가. **못 하게 막는 일은 페르소나의 몫이 아니다** — 금지·차단·한도는 6) 안전 체계 ↗가 맡는다.

- **목표와의 차이** — **목표**는 '이번 한 번의 과업'(매번 바뀜)이고, **페르소나와 원칙**은 '상시 적용되는 헌법'(일관성 유지)이다.
- **역할** — 페르소나가 명확해야 판단의 일관성이 유지되고, 조직의 톤앤매너와 브랜드 신뢰도를 지킬 수 있다.
- **금지는 왜 여기가 아닌가** — 시스템 프롬프트에 "절대 하지 마라"를 적어 둘 수는 있다. 그러나 그건 **지켜 주기를 부탁하는 문장**일 뿐이라, 프롬프트 인젝션 한 줄이나 긴 대화 뒤의 망각으로 무너진다. 실제로 **못 하게 만드는 것**은 코드가 실행 전후에 검사·차단·중단시키는 안전 체계다. 금지를 페르소나에만 적어 두고 막았다고 여기는 것이 흔한 사고 원인이다.
- **페르소나 3대 축** — ① **정체성**(Identity — 어떤 역할·전문성으로 일하는가) + ② **판단 기준**(Judgment — 갈릴 때 무엇을 우선하는가) + ③ **표현 방식**(Tone & Format — 어떤 문체·형식으로 내놓는가: 존댓말·문체·답변 길이·표/불릿 같은 산출물 형태). 셋 다 **'무엇을 한다'**는 서술이다. ※ ③은 사람이 읽는 에이전트(상담·문서·보고)에서 특히 중요하고, 사람이 볼 화면이 없는 에이전트(서버상주·API엔드포인트·스케줄 기동)에서는 비중이 작다.

## 2) LLM — 생각하는 엔진

주어진 상황과 입력을 분석하여 다음에 무엇을 할지 결정하는 **두뇌이자 추론 엔진**이다. 자율 루프에서 생각하고 판단하는 단계는 모두 LLM이 맡는다.

- **대표 모델** — Claude · GPT · Gemini · Grok · Llama 등. 같은 에이전트도 LLM을 교체하면 추론 성능과 비용이 달라진다.
- **한계와 역할** — LLM은 순수한 연산 모델이므로 직접 실행하지 못하며, 파일을 고치든 메일을 보내든 **실제 실행은 도구를 통해서만** 일어난다. 매 호출마다 토큰 비용이 발생한다.

### 🔧 심화 — 모델 선택 및 멀티 모델 라우팅 전략

선택 기준은 "**가장 거대한** 모델"이 아니라 "**해당 작업에 가장 최적화된** 모델"이다. 네 가지 요소를 저울질한다.

- **정확도** — 복합 추론과 아키텍처 설계가 필요하면 플래그십 모델(Claude Opus 등 각 제공사의 최상위 모델).
- **컨텍스트 길이** — 대용량 코드베이스나 문서를 통째로 넣어야 하면 대용량 컨텍스트 모델.
- **속도 및 비용** — 실시간 대화나 반복적 단순 추출은 싸고 빠른 경량 모델(Claude Haiku 등 각 제공사의 경량 모델).

실전 에이전트 시스템은 **모델 라우팅(Model Routing)**을 적용하여 어려운 계획 수립은 고급 모델에, 반복 도구 호출 및 단순 요약은 경량 모델에 분기 배정해 비용을 80% 이상 절감한다.

## 3) 목표 — 어디로 가고 어디서 멈추는가

목표는 단순히 끝내는 조건에 그치지 않고, **에이전트가 어디까지 움직일지를 정하는 경계선**까지 겸한다. 같은 "회의록 정리"라도 "1페이지 요약" vs "발언자별 상세 기록"으로 목표를 다르게 잡으면 동원하는 도구, 소요 시간, 산출물 형태가 완전히 달라진다.

- **표현 형식** — 자연어 지시("회의록 정리 후 발송"), JSON 스키마(구조화된 산출물 정의), 평가 함수(성공 여부 판정 조건식).
- **좋은 목표의 조건** — **달성할 결과물**과 **완료 조건(DoD, Definition of Done)**이 함께 있어야 한다. 루프 내에서 달성 여부를 검증할 수 있어야 하고(측정 가능성), 허용 범위를 엄격히 제한해야 한다.
- **나쁜 목표** — "알아서 잘 처리해라" 같은 모호한 지시는 내비게이션에 "좋은 곳으로 가줘"라고 찍는 것과 같다. 기준이 없어 자원을 낭비하며 무한 루프에 빠진다.

## 4) 지식베이스 — 판단과 작업에 활용하는 지식의 전체 체계

사전 학습된 LLM이 알지 못하는 **내 분야·내 회사·내 작업의 지식**을 공급하는 층이다. 지식베이스가 없으면 에이전트는 일반론만 말할 뿐 실무 맥락을 반영하지 못한다. 여기서 지식베이스는 참고할 문서만이 아니라 **업무 규칙, 결정의 근거, 작업 결과, 시행착오에서 얻은 교훈**까지 포함한다.

### 세 가지 질문으로 정한 4대 루트

지식을 연결하는 길은 네 갈래다. 이 넷은 임의로 나눈 것이 아니라 **세 가지 질문**의 답으로 갈린다.

| 질문 | 답 |
|---|---|
| 무엇을 미리 넣어둘까? | **① 직접 주입** |
| 무엇을 그때그때 찾아올까? | **② RAG** |
| 외부 시스템을 어떻게 연결할까? | 그 시스템의 방식에 맞춰 연결한다 → **③ API** / 표준 규격으로 연결한다 → **④ MCP** |

*(그림: 지식베이스 4대 루트 — 직접 주입과 RAG는 무엇을 아는 상태로 시작하느냐로, API와 MCP는 그 자료를 어떻게 끌어오느냐로 나뉜다. 네 루트에 모두 22가지 연결방법이 담긴다)*

| 루트 | 한 줄로 | 가짓수 |
|---|---|---|
| **① 직접 주입** | 필요한 자료와 기준을 함께 넣는다 | 9가지 |
| **② RAG** | 저장한 자료에서 근거를 찾아 답에 반영한다 / 검색 증강 생성(Retrieval-Augmented Generation) | 5가지 |
| **③ API** | 시스템의 기능을 직접 호출해 자료를 가져온다 / 응용 프로그램 인터페이스 — 프로그램끼리 주고받는 창구 | 4가지 |
| **④ MCP** | 공통 규격으로 자료와 도구를 연결한다 / 모델 컨텍스트 프로토콜 — 바깥 자료·도구를 찾아 쓰는 방식을 통일한 약속 | 4가지 |

> **나누는 축이 두 가지다.** ①직접 주입과 ②RAG는 **AI가 무엇을 아는 상태로 시작하느냐**로 나눈 것이고, ③API와 ④MCP는 **그 자료를 어떻게 끌어오느냐**로 나눈 것이다. 축이 둘이니 양쪽에 다 걸리는 연결방법이 나온다. **그래서 넷은 서로 배타적이지 않다** — 하나를 고르는 것이 아니라 겹쳐 쓴다.
> ※ ④ MCP는 지식만을 위한 통로가 아니라 **리소스·도구·프롬프트를 AI를 사용하는 프로그램에 연결하는 표준 프로토콜**이다. 여기서는 지식 원천을 연결하는 쓰임을 기준으로 함께 다룬다.

### 4대 루트에 담긴 22가지 연결방법

네 루트는 분류 이름일 뿐이고, 그 안에 실제 연결방법이 **모두 22가지** 들어 있다. 붙여넣기·파일 업로드 같은 익숙한 것부터 벡터 검색, 사내 시스템 조회, MCP 공개 서버, 브라우저 조작까지다. 22가지 전체 목록과 각 항목의 설명은 부록에 원문 그대로 실어 두었다.

### 자주 나오는 두 가지 질문

| 질문 | 답 |
|---|---|
| **우리 회사 DB는 어디에 해당하나?** | DB는 루트가 아니라 **자료가 있는 창고**다. 조회 결과를 복사해 넣으면 직접 주입이고, 관련 내용을 찾아 답에 반영하면 RAG다. 그 조회 기능을 API로 부를 수도, MCP로 연결할 수도 있다. **같은 자료가 4개 루트 어디로든 간다.** |
| **우리 자료로 AI를 학습시키고 싶다** | 학습시키는 것은 **파인튜닝**이라 부르며 모델의 가중치를 조정하는 방법이다. 22가지가 자료와 규칙을 **모델 밖**에 두고 참고하게 하는 것이라면, 파인튜닝은 **모델 안**에 새겨 넣는다. 여기서 다루는 지식베이스 연결은 전부 모델 밖의 일이다. |

### 메모리는 어디에 속하나

일하면서 쌓이는 지식, 즉 **메모리**는 별도의 다섯 번째 경로가 아니다. **장기 메모리**는 내가 따로 넣지 않아도 AI가 나에 관한 정보와 선호를 기억해 다음 대화에 쓰는 것이라, **①직접 주입 안에 들어간다**(22가지 중 04번).

> **단기 메모리는 지식베이스가 아니다.** 대화창 안의 임시 기억(컨텍스트)은 지금 돌고 있는 루프가 쥐고 있는 작업 기억이라, 지식을 *공급*하는 층이 아니라 **⑦ 자율 루프**가 도는 동안의 상태에 가깝다. 그래서 22가지 연결방법 어디에도 들어가지 않는다.
> ※ 장기 메모리는 편하지만 유의할 점이 있다 — 내가 적어 넣은 것이 아니라 AI가 요약해 둔 것이라, 원문과 어긋나 있어도 눈에 잘 띄지 않는다. **정확한 수치와 중요한 결정은 원본 기록을 따로 갖고 있어야 한다.**

### 🔧 심화 — RAG(검색 증강 생성)는 어떻게 지식을 찾아 넣나

**RAG(Retrieval-Augmented Generation)**는 LLM이 답하기 전에 **외부 지식 볼트에서 관련 문서를 먼저 검색하고, 그 내용을 프롬프트에 근거 자료로 첨부하여 응답을 생성**하는 기술이다.

- **1단계 (볼트 구축)** — 방대한 문서를 의미 단위 청크(Chunk)로 잘라 임베딩 벡터로 변환 후 벡터 DB에 저장.
- **2단계 (시맨틱 검색)** — 사용자 질문의 의미 벡터와 가장 유사한 문서 청크 상위 N개를 고속 추출.
- **3단계 (증강 생성)** — 추출된 문서를 시스템 프롬프트에 주입하여 LLM이 사실에 기반해 답하도록 강제.

RAG를 활용하면 모델 재학습 없이 사내 최신 데이터를 즉시 반영할 수 있고 출처 링크를 명시해 환각을 대폭 줄인다. 단, *지식 볼트에 담겨 있지 않은 정보는 여전히 알 수 없다*는 명확한 한계가 있다.

### 🔧 심화 — 장기 메모리 전용 제품 계층 (Mem0 · Letta · Zep)

단순 파일/DB 저장을 넘어, **Mem0 · Letta(구 MemGPT) · Zep** 같은 에이전트 전용 메모리 관리 계층이 독립된 컴포넌트로 표준화되고 있다.

이들 솔루션은 다회 세션에 걸친 사용자 선호도 추출, 오래된 기억의 지수 감쇠(Forgetting), 연관 기억의 자동 그래프 연결을 담당하여 에이전트가 시간이 지나도 맥락을 잃지 않게 돕는다.

## 5) 도구 — 결정을 행동으로 옮기는 손발

LLM은 순수한 연산 모델이라 스스로 실행하지 못하므로, 도구 없이는 결정을 내려도 실제 행동이 일어나지 않는다. 도구는 LLM의 결정을 **현실 환경의 물리적 행동으로 전환하는 실행 인터페이스**다.

- **기본 도구 (파일·셸·검색·API)** — 파일 읽기/수정, 터미널 명령 실행, 웹 검색, 외부 API 연동 등 시스템을 직접 조작하는 가장 기초적인 실행 단위다.
- **Python (코드 실행 & 오케스트레이션)** — 단순 고정 API를 넘어 즉석에서 코드를 짜 복잡한 계산·데이터 가공을 완결하는 만능 도구이자, 하위 도구들을 총괄 제어하는 최상위 집행자다.
- **도구 호출 메커니즘 (Tool Use)** — LLM이 JSON 규격으로 도구명과 인자를 요청하면, 런타임이 이를 물리적으로 실행하고 결과를 다시 LLM에 전달해 다음 판단을 유도한다.
- **스킬 (Skill)과의 관계** — 스킬은 도구의 일종이자 표준 작업 절차서(SOP)로, 호출되는 순간 사전 정의된 다단계 절차를 실행하는 도구로 작동한다.

### 🔧 심화 — 도구 계층에서 Python의 위치: 데스크톱형과 웹사이트형 비교

에이전트 아키텍처에서 Python(오케스트레이션 코드)은 개별 도구들과 나란히 놓이는 것이 아니라, **도구 목록의 최상위에서 전체 시스템을 지휘하고 통제하는 집행자**다. 배포 유형에 따라 1:1 전용 구조(데스크톱형)와 1:N 공유 구조(웹사이트형)로 나뉜다.

| 구분 | 데스크톱형 (1:1 전용) | 웹사이트형 (1:N 공유) |
|---|---|---|
| **오케스트레이터** | **`app/core/*.py`** / (Python 전용 코드) | **`agentLoop.ts`** / (단일 TS 오케스트레이션 엔진) |
| **하위 도구 제어** | Python이 SQLite, Playwright, CLI 등을 직접 호출·제어 | 중앙 REGISTRY를 통해 복수 에이전트에 균일 제공 |
| **자율 루프 집행** | 함수 호출 순서 및 재시도 순환을 Python 코드가 직접 집행 | tool-use 멀티 라운드 및 self_critique 피드백을 엔진이 집행 |
| **안전 체계 강제** | SSRF 차단, 로컬 파일 접근 권한 등 물리적 강제 | 도구 화이트리스트 검증, 토큰 한도 물리적 강제 |
| **핵심 구조** | 프로젝트마다 1벌의 Python 코드가 독립 동작 | **엔진 1곳 수정 = 복수 에이전트 전체에 즉시 파급**되는 고효율 구조 |

**💡 핵심 요약:** 데스크톱형이든 웹사이트형이든 **"오케스트레이션 코드가 최상위 도구이자 자율 루프·안전 체계의 실제 집행자"**라는 본질은 동일하다. 차이는 전용 코드 1벌을 프로젝트 혼자 쓰느냐(데스크톱형), 공유 엔진 1벌을 복수 에이전트가 나눠 쓰느냐(웹사이트형)에 있다.

### 🔧 심화 — Claude Code 도구 생태계 6종 (Tool · Skill · Command · MCP · Hook · Plugin) 상세 튜토리얼

대표적인 에이전트 네이티브 플랫폼인 **Claude Code**는 작업을 수행하고 통제하기 위해 아래 **여섯 가지 도구 체계**를 제공한다. (각 도구의 호출·설정 코드 포함)

**Tool**
함수처럼 즉시 실행되는 가장 기본 기능. 런타임이 LLM의 요청을 받아 물리적으로 실행한다.

- 용도: 파일을 읽고·쓰고·검색하고·셸 명령을 실행할 때.
- 대표 사례:
  - **Read** / **Edit** / **Write** — 파일 입출력 및 수정
  - **Bash** — 셸 명령 실행 (git, npm, build 등)
  - **Grep** — 코드베이스 텍스트 정밀 검색
  - **Agent** — 하위 서브에이전트에 작업 위임
- 호출 예 (LLM이 출력하는 JSON):
```
// LLM의 Tool Call 출력:
Read({ "file_path": "/src/app.ts" })
Bash({ "command": "git status" })
```

**Skill**
호출 시 사전에 정의된 표준 실행 절차(SOP)를 순차적으로 전개하는 매뉴얼 (SKILL.md).

- 용도: 다단계 복합 작업을 표준화하여 누구나 동일한 품질로 재현할 때 (재사용 자산화의 핵심).
- 대표 사례:
  - **skill-create** — 스킬 제작 자동화
  - **청룡-sal-grid-dev** — SAL Grid 방법론 강제 적용
  - **mbo-천상** — 상위 MBO 관리법에 따른 목표 관리 및 스킬 조율
- 호출 예:
```
사용자 입력: /skill-create
또는 LLM이 작업 맥락에 맞춰 자동 매칭 로드
```

**Command**
슬래시(/) 한 줄로 호출하는 사용자 정의 단축 명령.

- 용도: 자주 사용하는 복합 프롬프트를 단축키처럼 한 단어로 바인딩할 때.
- 대표 사례:
  - **/init** — 새 프로젝트 환경 및 CLAUDE.md 초기화
  - **/review** — 현재 PR 및 변경 코드 자동 검토
  - **/clear** — 대화 세션 컨텍스트 초기화
- 호출 예:
```
사용자가 터미널/입력창에 직접 입력:
/init
/review #42
```

**MCP**
Model Context Protocol — 외부 도구/데이터를 연결하는 개방형 표준 프로토콜. **'외부 세계로 통하는 범용 USB-C 포트'**. (2025-12 Linux Foundation 산하 AAIF로 이관된 업계 표준) 공식 스펙 ↗

- 용도: Gmail, Google Drive, Notion, 사내 ERP/DB 등 외부 능력을 안전하게 연결할 때.
- 대표 사례:
  - **claude_ai_Gmail** — 메일 송수신 및 검색
  - **claude_ai_Google_Drive** — 문서 접근
  - **사내 MCP 서버** — 내부 보안 DB 안전 연동
- 호출 예:
```
LLM이 MCP 프로토콜 규격으로 자동 호출:
mcp__claude_ai_Gmail__send_message({
  "to": "team@company.com",
  "subject": "주간 보고"
})
```

**Hook**
특정 이벤트 발생 시 시스템에 의해 강제 발동되는 이벤트 기반 가드레일 스크립트.

- 용도: 위험 명령 사전 차단, 수정 직후 자동 포맷팅 등 안전 규칙과 검증을 강제할 때.
- 대표 사례:
  - **PreToolUse** — Bash 실행 전 `rm -rf` 같은 위험 명령 차단
  - **PostToolUse** — 파일 수정 후 ESLint/Prettier 자동 실행
  - **Stop Hook** — 응답 완료 시점 자동 로깅 및 감사
- 설정 예 (~/.claude/settings.json):
```
"hooks": {
  "PreToolUse": [ { "command": "guard-check.sh" } ],
  "PostToolUse": [ { "command": "npm run lint" } ]
}
```

**Plugin**
도구 묶음(Tool·Skill·Command·MCP·Hook)을 단일 패키지로 번들링한 배포 단위.

- 용도: 검증된 도구 세트를 팀이나 커뮤니티에 원클릭으로 설치·공유하고 버전 관리할 때.
- 대표 사례:
  - **oh-my-wiki** — Obsidian 지식 베이스 자동화 번들
  - **frontend-design** — 디자인 시스템 가이드 플러그인
- 설치 예 (공식 플러그인 마켓플레이스):
```
/plugin marketplace add <owner>/<repo>
/plugin install <plugin-name>
```

## 6) 안전 체계 — 터질 위험을 막고 점검하는 방어선

에이전트가 스스로 강력하게 움직이는 만큼, 오작동 시의 위험도 크다. Gartner는 2027년까지 기업 에이전트 프로젝트의 40% 이상이 리스크 및 비용 관리 미흡으로 취소될 것이라 전망한다. 안전 체계는 **① 위험 식별(무엇이 터질 수 있나) → ② 방어 장치(무엇으로 막나) → ③ 점검 장치(잘 막고 있는지 어떻게 아나)**라는 3단계 논리로 구축된다.

### 위험 6가지 & 방어 장치 5가지 (가드레일)

| 방어 장치 (가드레일) | 하는 일 | 막는 위험 (6대 리스크) |
|---|---|---|
| **입력 검사** | 개인정보 필터링, 악성 지시어 탐지 | **명령 가로채기(프롬프트 인젝션)** / OWASP Top 10 for Agentic Apps (ASI01) |
| **출력 검증** | 근거 확인, 유해성 점검, AI 생성물 표시 의무 준수 | **환각(Hallucination)**, **법적 의무** / 2026-01-22 AI 기본법 및 07-21 고시 준수 |
| **한도 설정** | 반복 횟수·시간·토큰·비용 상한선 강제 (최소 대리권) | **무한 루프**, **비용 폭주** |
| **사람 승인** / Human-in-the-loop | 결제·삭제·외부 전송 등 위험 행동 직전 사람 확인 | 돌이킬 수 없는 치명적 사고 방지 |
| **자동 복구** | 실패 시 재시도, 주 모델 장애 시 예비 모델 자동 폴백 | **서버 장애** 및 서비스 중단 |

**심층 방어(Defense in Depth) 원칙** — 위험 하나에 여러 겹의 방어선을 둔다. 예컨대 프롬프트 인젝션은 입력 검사가 1차 차단하고, 뚫리더라도 위험 행동 직전의 사람 승인이 최후 방어선이 된다.

### 점검 장치 3가지 (관측성 & 거버넌스)

사람이 매번 부르지 않는 에이전트(서버상주·API엔드포인트·스케줄 기동)에서는 이 점검 장치가 유일한 눈이다.

- **과정 기록 (Trace)** — 에이전트의 모든 추론과 도구 호출 스팬(Span)을 단계별로 기록한다.
- **품질 평가 (Evals)** — 완료된 결과물이 목표에 맞는지 외부에서 점수를 매기고 검증한다.
- **비용 집계 (Cost Tracking)** — 토큰·API 비용과 실행 시간을 실시간 모니터링한다.

> 핵심은 *"정상 완료"를 막연한 신뢰가 아니라 검증 가능한 로그와 지표로 입증하는 것*이다.

### 🔧 심화 — 실전 AI 에이전트 관측성(Observability) & 거버넌스 도구 생태계

프로덕션 환경에서는 관측 및 거버넌스를 전담하는 전문 도구를 결합하여 안정성을 확보한다.

- **추적 및 디버깅 (Tracing)** — **LangSmith** (단계별 추론 및 도구 호출 전체 Trace 시각화)
- **평가 및 메트릭 (Evals)** — **Langfuse** (프롬프트 버전 관리 및 응답 점수 평가, 2026-01 ClickHouse 인수)
- **비용 및 지연시간 (Cost/Latency)** — **Helicone** (실시간 토큰 비용 및 API 프록시 모니터링)
- **모델 드리프트 감시 (Monitoring)** — **Arize Phoenix** (시간 경과에 따른 성능 저하 및 임베딩 드리프트 추적)
- **가드레일 및 정책 강제 (Safety)** — **Guardrails AI** (출력 스키마 강제 및 금기어 필터링)
- **인젝션 방어 (Security)** — **Lakera** (2025-09 Check Point 인수), **LlamaGuard** (악성 프롬프트 실시간 방어)

현재 업계는 **OpenTelemetry(OTel)** 표준 기반으로 관측 인터페이스를 단일화하는 추세다.

## 7) 자율 루프 — 사람 지시 없이 도는 순환

"자율"의 핵심은 **사람이 매 단계를 일일이 시키지 않아도** 에이전트가 스스로 다음 행동을 골라 실행한다는 점이다. 아래 순환이 목표 달성까지 반복된다.

*(그림: 자율 루프 순환도 — 현재 상태 파악 → 계획 → 실행 → 결과 확인 → 평가 → 수정을 거쳐 실행으로 피드백하고 목표 달성 시 종료한다)*

영문 표기 — ① Observe · ② Plan · ③ Act · ④ Observe result · ⑤ Evaluate · ⑥ Refine

> **6단계를 메일 답장 예시로 보기**
>
> - **① 현재 상태 파악 (Observe)** — 받은편지함에 미답장 메일 5통이 있음을 인지.
> - **② 계획 (Plan)** — 긴급도에 따라 순서를 수립하고, 첫 번째 답장 대상 선정.
> - **③ 실행 (Act)** — 메일 도구를 호출해 답장 작성 및 발송.
> - **④ 결과 확인 (Observe result)** — 발송 성공 여부와 잔여 메일 수 확인.
> - **⑤ 평가 (Evaluate)** — 답장 내용이 목표에 부합하는지, 누락은 없는지 자체 검증.
> - **⑥ 수정 (Refine)** — 미흡한 점을 보완하여 **③ 실행 단계로 피드백(재실행)**. 5통이 모두 완료되면 종료.
>
> 특히 ④~⑥(결과 확인·평가·수정)으로 이어지는 **자기 교정(Self-Correction) 피드백 구간**이야말로 에이전트와 단순 자동화를 가르는 결정적 차이다.

> **루프가 도는 동안의 작업 기억이 단기 메모리다.** 직전 단계의 결과, 방금 받은 피드백, 지금까지 시도한 것 — 대화창 안의 임시 기억(컨텍스트 창)이 여기에 해당한다. 루프가 끝나면 사라지고, 남겨야 할 것만 **장기 메모리**로 넘어가 지식베이스 **①직접 주입**에 쌓인다. 그래서 단기 메모리는 지식을 *공급*하는 층이 아니라 루프가 쥐고 있는 **상태**다.

### 🔧 심화 — 자율 루프의 다양한 구현 아키텍처 (ReAct · Plan-and-Execute · 하네스형)

본 튜토리얼의 6단계 순환 외에도, 구현 목적과 효율성에 따라 다양한 루프 패턴이 존재한다.

| 아키텍처 패턴 | 작동 메커니즘 | 특징 및 적합한 과업 |
|---|---|---|
| **ReAct** / Reason + Act | 생각(Thought) → 행동(Action) → 관찰(Observation)의 초단기 루프 | 가장 보편적인 구현체. 탐색적 과업에 강력하나 단계가 길어지면 토큰 소모 큼 |
| **Plan-and-Execute** | 전체 계획 일괄 수립 → 순차적 도구 실행 → 최종 결과 검증 | LLM 호출 횟수를 최소화하여 비용을 아끼고 구조화된 작업에 유리 |
| **3박자 압축형** | 인지(Perceive) → 추론(Reason) → 행동(Act) | 에이전트 제어 루프의 가장 직관적인 최소 단위 표현 |
| **하네스식 7단계** | 목표이해 → 계획 → 스킬선택 → 도구실행 → 관찰 → 검증 → 컨텍스트 갱신 | 스킬 로딩과 상태 보존을 명시적으로 분리한 엔터프라이즈 실무형 패턴 |

### 🔧 심화 — 에이전트 간 협업 6대 패턴과 A2A(Agent-to-Agent) 통신 규격

복잡한 시스템에서는 단일 에이전트가 아닌 여러 에이전트가 역할을 분담하는 **멀티 에이전트 아키텍처**를 구성한다.

- **순차 실행 (Sequential)** — A의 출력이 B의 입력이 되는 파이프라인 릴레이.
- **병렬 분산 (Parallel)** — 독립적인 하위 과업을 여러 에이전트가 동시에 처리 후 병합.
- **조건 분기 (Routing)** — 중앙 라우터가 입력 유형에 따라 전문 에이전트로 전달.
- **반복 정제 (Loop/Iterative)** — 만족할 기준이 나올 때까지 작성자와 검토자가 핑퐁.
- **계획-실행-검증 (Plan-Do-Check)** — 아키텍트, 빌더, 테스터 에이전트가 3각 협업.
- **동적 조율 (Orchestration)** — 상위 오케스트레이터가 실시간으로 하위 에이전트를 생성·위임.

도구를 연결하는 규격이 **MCP**라면, **에이전트끼리 서로를 탐색하고 작업을 위임하는 표준 규격**은 **A2A (Agent-to-Agent Protocol)**이다 (2026-03 v1.0 확정, Linux Foundation 산하 글로벌 표준화 진행 중).
