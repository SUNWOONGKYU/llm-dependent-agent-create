## 1. 목표

**이름과 정의**: 목표는 무엇을 어디까지 해내야 끝인지 정하는 조건이다. 좋은 목표에는 만들어 낼 결과물에 대한 명확한 정의와, 어느 수준에 이르면 작업을 끝내야 하는지를 정해 놓은 완료 조건이 함께 들어 있어서 무엇을 얼마나 달성했는지 측정할 수 있다.

**무엇을 정하는가**: 에이전트가 만들어야 할 결과물의 모습과, 언제 끝난 것으로 볼지의 기준을 정한다. 이 둘이 함께 있어야 측정 가능한 목표가 된다.

**질문 목록**
| 확인할 것 | 무엇을 묻나 | 질문 문구 예시 | 모르겠어요 기본값 |
|---|---|---|---|
| 결과물 정의 | 에이전트가 만들어 내야 할 결과물이 구체적으로 무엇인지 | "이 에이전트가 한 줄로 뭘 만들어 내야 하나요? 예: '회의록을 한국어 요약 3줄로 만든다', '받은 이메일을 5개 종류로 나눠 분류한다'" | 처음 말한 요청 문장을 결과물 정의로 임시 채택하고 뒤에서 다시 확인한다 |
| 완료 조건 | 언제 끝난 것으로 볼지 기준(정상적으로 다 됐다고 보는 기준) | "이 결과물이 다 됐다고 볼 수 있는 기준이 있나요? 예: '이메일 다섯 통 모두에 답장하면 끝', '스스로 채점해서 4점 이상이면 끝'" | 5점 만점 자가평가에서 4점 이상이면 끝난 것으로 본다 |

**다른 요구 항목과의 경계**
- 목표 vs 안전 체계: 하지 말아야 할 일과 해도 되는 일의 범위는 목표가 아니라 안전 체계가 정한다. 목표는 결과물 정의와 완료 조건까지만이다.
- 목표 vs 페르소나: 목표는 이번 작업이 어디까지 가야 끝인지 정하는 조건이고, 페르소나는 일하는 내내 유지되는 정체성이다.
- 목표 vs 종료 조건(안전 체계 확인할 것): 완료 조건은 정상적으로 일을 마쳤다고 보는 기준이고, 종료 조건은 정상적으로 끝나지 않을 때 강제로 멈추는 횟수·시간 상한이다.

**앞에서 답해야 하는 것(의존)**: 없음. 12개 요구 항목 가운데 가장 먼저 물어도 되는 요구 항목이다. 다만 사용자 층을 먼저 알면 결과물 정의 질문의 눈높이를 맞추기 좋다(병행 가능, 순서를 강제하지는 않음).

**산출물**: `plan.md` §2 🎯목표(입력 → 사람 개입 지점 → 최종 산출물, 완료 기준), 목표서 삽입절 🎯②목표, Phase 5 체크리스트 항목 1(7대 구성요소 명시)·3(목표서 대조).

## 2. 페르소나

**이름과 정의**: 페르소나는 시작할 때 LLM에 부여하는 정체성으로, 이 에이전트가 무엇을 어떻게 하는 존재인지를 정한다. 무엇을 하는지가 역할이고, 어떻게 하는지가 판단 기준과 표현 방식이다. 하지 말라는 금지 사항은 페르소나가 맡지 않는다. 금지 사항은 안전 체계가 맡는다.

**무엇을 정하는가**: 에이전트가 어떤 역할로, 무엇을 우선해 판단하며, 어떤 문체·형식으로 결과를 내놓을지를 정해 같은 일을 맡겨도 결과가 일관되게 나오도록 한다.

**질문 목록**
| 확인할 것 | 무엇을 묻나 | 질문 문구 예시 | 모르겠어요 기본값 |
|---|---|---|---|
| 역할 | 무엇을 하는 존재인지(전문성·직함) | "에이전트가 어떤 역할로 일하면 좋을까요? 예: '꼼꼼한 실무 조교', '경험 많은 컨설턴트'" | 도메인 전문가 역할로 시작 |
| 판단 기준 | 판단이 나뉠 때 무엇을 우선하는지 | "여러 선택지 중 고를 때 뭘 가장 먼저 볼까요? 예: '정확성 먼저, 확인 안 된 건 단정하지 않는다', '속도 먼저, 대략이라도 빨리'" | 정확성을 우선하고, 확인 안 된 사실은 단정하지 않는다 |
| 표현 방식 | 작업 결과를 어떤 문체·형식으로 제시하는지 | "결과를 어떤 말투와 모습으로 받고 싶으세요? 예: '정중한 존댓말, 표로 정리', '짧고 편하게, 불릿만'" | 정중한 존댓말, 핵심만 불릿으로 정리 |

**다른 요구 항목과의 경계**
- 페르소나 vs 목표: 위 「1. 목표」 참조.
- 페르소나 vs 안전 체계: 금지 사항(하지 말 것)은 페르소나가 아니라 안전 체계가 맡는다. 시스템 프롬프트에 "하지 마라"를 적어 두는 것만으로는 실제로 막아지지 않는다.
- 페르소나 vs 사용자 층: 사용자 층은 누가 쓰는지를 보는 바깥 축이고, 페르소나는 에이전트가 누구로서 일하는지를 보는 안쪽 축이다.

**앞에서 답해야 하는 것(의존)**: 목표(무엇을 만들어야 하는지 알아야 어떤 역할·판단 기준이 필요한지 정할 수 있다), 사용자 층(표현 방식의 비중이 달라진다. 사람이 읽는 화면이 있는 에이전트는 표현 방식이 중요하고, 화면이 없는 에이전트는 비중이 작다), 출력(사람이 직접 보는 화면인지 여부).

**산출물**: `plan.md` §2 🎭페르소나(역할 한 줄, 문체·태도, 근거 규칙 목록) → `app/skills/persona.md`, 목표서 삽입절 🎭①페르소나, Phase 5 체크리스트 항목 1.

## 3. LLM

**이름과 정의**: LLM은 다음에 무엇을 할지 결정하는, 사람의 두뇌와 같은 역할을 하는 추론 엔진이다. LLM에는 여러 가지가 있고(클로드, 지피티, 제미나이, 그록, 라마), LLM마다 또 여러 모델이 있다. 어려운 판단이 필요한 작업에는 비싼 모델을, 반복되는 쉬운 작업에는 싼 모델을 쓴다. 다만 LLM은 직접 실행하지 못한다. 실제 실행은 도구를 통해서만 할 수 있다.

**무엇을 정하는가**: 어느 LLM을 1순위로 쓰고, 그 LLM이 막히거나 비용 한도를 넘었을 때 어느 순서로 대신 쓸지를 정한다. 필요하면 그 LLM 안에서도 어느 모델(비싼 모델 또는 싼 모델)을 쓸지까지 정한다.

**질문 목록**
| 확인할 것 | 무엇을 묻나 | 질문 문구 예시 | 모르겠어요 기본값 |
|---|---|---|---|
| 1순위 LLM | 어느 LLM을 먼저 쓸지 | "어느 LLM을 1순위로 쓸까요? 예: 클로드(균형 잡힌 일반 작업), 지피티(코드 작성), 제미나이(이미지·긴 문서), 그록(실시간 정보)" | 클로드 |
| 폴백 LLM 순서 | 1순위가 막힐 때 다음 순서 | "1순위가 안 되면(오류나 한도 초과) 다음은 어느 LLM으로 넘어갈까요? 예: '클로드 안 되면 제미나이, 그다음 지피티'" | 클로드 → 제미나이 → 지피티 → 그록 순서로 돌아가며 대체 |
| 모델 선택(조건부) | 고른 LLM 안에서 어느 모델을 쓸지 | "이 LLM 안에도 여러 모델이 있어요. 어려운 판단이 잦은 작업인가요, 정해진 대로 반복하는 작업인가요? 어려운 판단이 잦으면 비싼 모델(느리지만 판단이 깊음), 반복 작업이면 싼 모델(빠르고 저렴함)을 씁니다" | 비싼 모델과 싼 모델을 자동으로 나눠 맡기는 표준 배정(어려운 계획은 비싼 모델, 반복되는 호출은 싼 모델)을 적용한다. 대상 LLM에 여러 모델이 없으면 이 질문은 건너뛴다 |

**다른 요구 항목과의 경계**
- LLM vs 도구: LLM은 판단만 한다. 실제 실행은 도구를 통해서만 일어난다.
- LLM vs 안전 체계(비용 한도): 어떤 LLM·모델을 쓸지는 LLM 요구 항목이 정하고, 그것을 얼마나 쓸 수 있는지의 상한은 안전 체계가 정한다.
- LLM vs 모델: LLM은 클로드·지피티·제미나이·그록·라마처럼 서로 다른 회사·계열을 가리키고, 모델은 그 LLM 안에서 고르는 버전(비싼 모델·싼 모델)이다. 1순위·폴백은 LLM 층위의 질문이고, 모델 선택은 그 안의 하위 층위 질문이다.

**앞에서 답해야 하는 것(의존, 확인할 것 단위)**: 1순위 LLM·폴백 LLM 순서는 목표(어떤 작업인지 알아야 LLM 성격을 고를 수 있다)와 도구(코드·이미지·실시간 검색 등 작업 성격이 도구 목록에서 드러난다)에 의존한다. "모델 선택(조건부)"만 추가로 자율 루프(반복 여부·어려운 판단의 빈도에 따라 모델 선택이 달라진다)에 의존한다. LLM 요구 항목 전체가 자율 루프에 의존하는 것은 아니다.

**산출물**: `plan.md` §2 🤖LLM(1순위 → 폴백, 모델 선택, API 키 여부), 목표서 삽입절 🤖③LLM, BOM 🔵 LLM 폴백 체인 모듈, Phase 5 체크리스트 항목 3.

## 4. 지식베이스

**이름과 정의**: 지식베이스는 내 분야, 내 회사, 내 작업에 필요한 지식을 에이전트와 연결하는 것이다. 연결하는 방법은 네 가지다(직접 주입, RAG, API, MCP). 네 가지는 서로 배타적이지 않아서 함께 쓸 수 있다. 일하면서 쌓이는 메모리도 직접 주입 쪽에 속한다.

**무엇을 정하는가**: 판단에 쓸 지식을 언제·어떻게 연결할지, 그리고 일하면서 쌓이는 지식(메모리)을 기억해 둘지를 정한다.

**질문 목록**
| 확인할 것 | 무엇을 묻나 | 질문 문구 예시 | 모르겠어요 기본값 |
|---|---|---|---|
| 지식 연결 방법 | 판단에 필요한 자료를 어떻게 쓰게 할지 | "판단에 필요한 자료를 어떻게 쓰게 할까요? ① 자료를 미리 넣어 둔다(직접 주입) ② 필요할 때마다 찾아오게 한다(RAG) ③ 외부 시스템 기능을 그대로 불러온다(API) ④ 표준 규격으로 여러 자료·도구를 한꺼번에 연결한다(MCP). 여러 개를 같이 골라도 됩니다" | 필요한 자료를 미리 넣어 두는 방식(직접 주입)만 우선 적용 |
| 메모리(작업 지식) | 이전에 처리한 내용을 기억해야 하는지 | "이전에 처리한 내용을 기억해야 하나요? 예: '한 번 쓰고 잊어도 된다', '사용자별로 계속 기억한다', '중복 처리 방지용으로만 기록한다'" | 한 번 쓰고 잊는다(기억 없음) |

**다른 요구 항목과의 경계**
- 지식베이스 vs 도구: 참고만 하면 지식베이스, 실행하거나 결과를 기록·변경하면 도구다. 예: 고객 DB를 조회만 하면 지식베이스, 그 DB에 값을 써넣으면 도구다.
- 지식베이스 vs 자율 루프(단기 메모리): 지금 도는 루프 안에서만 쓰는 임시 작업 기억은 지식베이스가 아니라 자율 루프가 쥐고 있는 상태다. 루프가 끝나고도 남겨야 할 것만 지식베이스(메모리)로 넘어간다.
- 지식베이스 vs 입력: 입력은 이번 한 건을 처리하려고 그때 들어오는 자료이고, 지식베이스는 미리 갖춰 두고 여러 건에 걸쳐 계속 참고하는 판단 근거다.

**앞에서 답해야 하는 것(의존, 확인할 것 단위)**: 지식 연결 방법은 목표(무엇을 판단하는 데 지식이 필요한지 알아야 한다)에 의존한다. "메모리(작업 지식)"만 추가로 자율 루프(반복형인지 아닌지에 따라 메모리 필요성이 달라진다)에 의존한다. 지식베이스 요구 항목 전체가 자율 루프에 의존하는 것은 아니다.

**산출물**: `plan.md` §2 📘지식베이스(직접 주입 파일 목록, RAG 자료, API, MCP, 작업 지식 `state.json`), 목표서 삽입절 📘④지식베이스, Phase 5 체크리스트 항목 1.

## 5. 도구

**이름과 정의**: 도구는 LLM이 결정한 것을 실제로 실행하는 수단이다. 기본 도구는 파일을 읽고 쓰는 도구, 명령어를 실행하는 셸, 정보를 찾는 검색이다. 파이썬은 코드를 실행해 여러 도구를 한꺼번에 조합해 쓸 수 있어 한 단계 위에서 도구들을 지휘한다. 스킬은 특정 작업을 어떤 순서로 처리할지 정리해 둔 작업 절차서로, 에이전트가 필요할 때 불러 쓰는 도구이기도 하다.

**무엇을 정하는가**: 에이전트가 실제로 무엇을 실행할 수 있게 할지(파일 읽고 쓰기, 셸 명령, 검색, 파이썬, 스킬, 외부 API·MCP 호출 등)를 정한다.

**질문 목록**
| 확인할 것 | 무엇을 묻나 | 질문 문구 예시 | 모르겠어요 기본값 |
|---|---|---|---|
| 외부 도구 필요 여부 | 외부 정보·서비스를 실제로 다뤄야 하는지 | "에이전트가 외부 정보·서비스를 실제로 다뤄야 하나요? 예: 웹 검색, 파일 읽기·쓰기, 이메일 전송, DB에 값 저장. 없으면 '없음'이라고 답해도 됩니다" | 기본 도구(파일 읽기·쓰기, 검색)만 두고, 필요해지면 나중에 추가한다 |

**다른 요구 항목과의 경계**
- 도구 vs 지식베이스: 위 「4. 지식베이스」 참조.
- 도구 vs 출력: 도구는 결과를 실제로 내보내는 실행 수단이고(예: 이메일 발송 기능), 출력은 그 결과가 어디로 어떤 모습으로 가야 하는지의 요구사항이다. 같은 작업을 다른 축에서 본 것이라 겹쳐 보일 수 있다.

**앞에서 답해야 하는 것(의존)**: 목표(무엇을 해내야 하는지), 입력(자료를 어디서 가져와야 하는지), 출력(결과를 어디로 내보내야 하는지).

**산출물**: `plan.md` §2 🔧도구(용도·구현·AI 개입 표), 목표서 삽입절 🔧⑤도구, BOM 부품 매핑, Phase 5 체크리스트 항목 1.

## 6. 안전 체계

**이름과 정의**: 안전 체계는 에이전트가 일으킬 수 있는 위험을 막고 점검하는 체계다. 하지 말아야 할 일과 해도 되는 일의 범위를 여기서 정한다. 안전 체계는 위험 식별 장치, 방어 장치, 점검 장치, 세 계층으로 구성되고 세 계층은 동시에 작동한다.

**무엇을 정하는가**: 비용이 얼마나 쌓이면 멈출지, 얼마나 반복하거나 오래 돌면 멈출지, 실패했을 때 무엇을 할지, 민감한 정보를 어떻게 다룰지를 정한다.

**질문 목록**
| 확인할 것 | 무엇을 묻나 | 질문 문구 예시 | 모르겠어요 기본값 |
|---|---|---|---|
| 비용 한도(1회) | 한 번 실행할 때 비용 상한 | "한 번 실행할 때 비용이 얼마를 넘으면 멈출까요? 예: 500원, 1,000원, 한도 없음" | 1회 500원 |
| 비용 한도(월 누적) | 한 달 누적 비용 상한 | "한 달 동안 다 합쳐서 얼마까지 쓸 수 있을까요? 예: 50,000원, 100,000원, 한도 없음" | 월 50,000원 |
| 종료 조건 | 몇 번, 또는 얼마나 오래 시도하다 멈출지(횟수·시간 한도) | "같은 일을 몇 번까지, 또는 얼마나 오래 시도하다 멈출까요? 예: '3번 안 되면 멈춤', '5분 넘으면 멈춤'" | 3회 또는 5분 중 먼저 오는 쪽에서 멈춘다 |
| 실패 시 처리 | 일이 실패했을 때 무엇을 할지 | "일이 실패하면(예: 도구가 응답하지 않음, 답을 못 찾음) 어떻게 할까요? ① 자동으로 다시 시도한다 ② 사람에게 확인을 구하고 기다린다 ③ 실패했다고 알리고 멈춘다" | 자동으로 다시 시도하되(최대 3회) 그래도 안 되면 실패를 알리고 멈춘다 |
| 보안(개인정보) | 다루는 정보에 개인정보가 있는지, 그리고 그 정보가 어디까지 외부로 나가는지(★V4.11 — 외부 전송 범위에 LLM 제공자 전달을 반드시 포함) | "에이전트가 다루는 정보에 개인정보(이메일·전화번호 등)가 섞여 있나요? 있다면 그 정보가 화면·저장 파일뿐 아니라 LLM 제공자(API 호출이든 CLI 호출이든, 원문을 그대로 보내든 가린 뒤 보내든)에게도 전달되는지까지 포함해서 답해 주세요." | 개인정보 없음으로 가정하고 시작하되, LLM 제공자에게 보내는 내용에도 개인정보가 섞이지 않는지 별도로 확인한다. 나오면 다시 확인 |
| 보안(보관 기간) | 처리한 자료를 얼마나 보관할지 | "처리한 자료를 얼마나 보관할까요? 예: 처리 후 바로 삭제, 30일 보관, 기한 없이 보관" | 처리 후 바로 삭제 |
| 도메인 가드 | 이 에이전트가 다루는 분야 특유의 위험을 막을 규칙이 있는지 | "이 에이전트가 다루는 분야에서 절대 하면 안 되는 것이 있나요? 예: 법률 상담이면 확정적인 법적 판단 금지, 의료 상담이면 진단 확정 금지, 금융이면 투자 권유 금지" | 도메인 가드 없음으로 시작하고, 위험이 드러나면 다시 확인한다 |

**다른 요구 항목과의 경계**
- 안전 체계 vs 목표: 범위(하지 말아야 할 일, 해도 되는 일)는 안전 체계가 정하고, 결과물 정의와 완료 조건은 목표가 정한다.
- 안전 체계 vs 자율 루프: 자율 루프는 순환 그 자체(관찰, 계획, 실행, 결과 확인, 평가, 수정)이고, 안전 체계는 그 순환을 막고 점검하는 장치다.
- 종료 조건 vs 완료 조건(목표): 완료 조건은 목표를 정상적으로 달성해서 끝난 것이고, 종료 조건은 정상적으로 끝나지 않을 때 강제로 멈추는 횟수·시간 상한이다. "결과가 충분히 좋으면 멈춘다"는 선택지는 종료 조건이 아니라 완료 조건 쪽에 있다.
- 실패 시 처리 vs 종료 조건: 실패 시 처리는 한 번의 실패에 어떻게 대응하는지(재시도, 확인, 중단)이고, 종료 조건은 그런 시도가 누적됐을 때 전체를 멈추는 상한이다.
- 도메인 가드 vs 보안: 보안은 개인정보·보관 기간처럼 모든 에이전트에 공통되는 위험을 다루고, 도메인 가드는 이 에이전트가 다루는 분야에서만 생기는 특유의 위험(예: 법률·의료·금융)을 막는다.

**앞에서 답해야 하는 것(의존, 확인할 것 단위)**: 비용 한도(1회·월 누적)는 LLM(모델 비용이 비용 한도의 기준이 된다)에 의존한다. 종료 조건은 목표(완료 조건과 구분해야 한다)와 자율 루프(반복형인지에 따라 종료 조건의 의미가 달라진다)에 의존한다. 실패 시 처리는 도구(무엇을 실행하는지 알아야 실패 시 처리를 구체적으로 정할 수 있다)에 의존한다. 보안(개인정보)은 도구가 아니라 입력(그때 들어오는 자료에 개인정보가 섞여 있는지)과 지식베이스(미리 연결해 둔 자료에 개인정보가 섞여 있는지)에 의존한다. 도메인 가드는 목표(다루는 분야를 알아야 도메인 특유의 위험을 정할 수 있다)에 의존한다. 보안(보관 기간)은 앞선 어느 요구 항목에도 의존하지 않는다.

**응답 속도(성능) 한도**: 이 요구 항목의 질문으로 묻지 않는다. 자율 루프의 동시성·timeout 등 코드 기본값으로 처리한다.

**산출물**: `plan.md` §2 🛡️안전 체계(종료, 보안, 비용, 도메인 가드), §5 실패 모드 표, 목표서 삽입절 🛡️⑥안전 체계(🛑종료, 🔐보안, 💰비용·성능, 🚫도메인 가드), Phase 5 체크리스트 항목 9(실패 모드 정의).

## 7. 자율 루프

**이름과 정의**: 자율 루프는 목표를 달성할 때까지 에이전트가 사람의 지시 없이 스스로 돌리는 순환 과정이다. 관찰하고, 계획하고, 실행하고, 결과를 확인하고, 평가하고, 부족하면 수정한다. 이 가운데 결과를 확인하고 평가해서 스스로 고치는 부분이, 정해진 순서대로만 도는 자동화와 결정적으로 다른 점이다.

**무엇을 정하는가**: 에이전트가 한 번만 답하고 끝낼지, 반복해서 스스로 돌지, 그리고 언제 그 순환을 시작할지(트리거)를 정한다. 반복 실행이라면 여러 건을 동시에 처리할지, 실패한 건은 몇 번 다시 시도할지, 중간에 멈추면 어디서부터 다시 시작할지도 함께 정한다.

**질문 목록**
| 확인할 것 | 무엇을 묻나 | 질문 문구 예시 | 모르겠어요 기본값 |
|---|---|---|---|
| 자율 루프 형태 | 1회성인지, 반복 자율 수행인지 | "혼자 한 번에 끝나는 일인가요, 아니면 같은 작업을 반복해서 스스로 도는 일인가요? 예: '1회 호출하면 답 하나 주고 끝', '받은 이메일이 남아 있는 동안 계속 반복'" | 1회 호출형(한 번 실행하고 끝) |
| 트리거 | 언제 이 순환이 시작되는지 | "이 에이전트가 언제 깨어나면 좋을까요? 예: ① 매일 같은 시각 ② 사용자가 버튼을 누를 때 ③ 새 이메일이 도착할 때" | 사용자가 버튼을 누를 때(수동 실행) |
| 동시성·재시도·재개 정책(조건부, 반복 실행일 때만) | 여러 건을 한꺼번에 처리하는지, 실패한 건은 몇 번 다시 시도하는지, 멈추면 어디서부터 다시 시작하는지 | "이 에이전트가 여러 건을 한꺼번에 처리하나요, 한 번에 한 건씩인가요? 한꺼번에 처리한다면 최대 몇 건까지 동시에 처리할까요? 실패한 건은 몇 번까지 다시 시도할까요? 중간에 멈추면 처음부터 다시 할까요, 멈춘 자리부터 이어갈까요?" | 한 번에 한 건씩 순차로 처리하고, 실패하면 3회까지 다시 시도하며, 멈추면 처음부터 다시 한다(재개 없음) |

자율 루프 형태가 1회성(1회 호출형)이면 동시성·재시도·재개 정책 질문은 생략하고 위 기본값(1건씩 순차)으로 갈음한다.

**다른 요구 항목과의 경계**
- 자율 루프 vs 안전 체계: 위 「6. 안전 체계」 참조.
- 자율 루프 vs 목표: 목표는 어디서 멈추는지의 기준(완료 조건)이고, 자율 루프는 그 기준에 이를 때까지 도는 순환 그 자체다.
- 자율 루프(트리거) vs 입력: 트리거는 언제 시작하는지(시점)이고, 입력은 시작할 때 무엇을 받는지(내용)다.
- 자율 루프(동시성·재시도·재개 정책) vs 안전 체계(종료 조건·실패 시 처리): 종료 조건·실패 시 처리는 언제 멈추는지·실패에 어떻게 반응하는지의 상한이고, 동시성·재시도·재개 정책은 반복 실행 자체의 처리량과 재개 방식을 정하는 것이다. 재시도라는 말이 겹쳐 보이지만, 안전 체계 쪽은 전략(재시도할지·확인할지·중단할지)을 정하고 이 확인할 것은 몇 건을 동시에·어디서부터 재개할지를 정한다.

**앞에서 답해야 하는 것(의존)**: 목표(완료 조건이 있어야 루프가 언제 멈추는지 정할 수 있다), 도구(실행 단계에서 무엇을 실제로 할지), 입력(트리거로 무엇이 도착해야 시작하는지).

## 8. 입력

**이름과 정의**: 입력은 에이전트가 일을 시작하기 위해 받는 자료다.

**무엇을 정하는가**: 에이전트에게 무엇이 어떤 모습으로 도착해야 일을 시작할 수 있는지를 정한다.

**질문 목록**
| 확인할 것 | 무엇을 묻나 | 질문 문구 예시 | 모르겠어요 기본값 |
|---|---|---|---|
| 입력 내용 | 일을 시작하려면 무엇을 받아야 하는지 | "에이전트가 일을 시작하려면 무엇을 받아야 하나요? 예: 회의 녹음 파일, 정리할 텍스트, 처리할 이메일 한 통" | 사용자가 채팅창에 직접 입력하는 텍스트 한 건 |
| 입력 형식 | 그 자료가 어떤 모습으로 오는지 | "그 자료가 어떤 모습으로 오나요? 예: 자유롭게 쓴 글, 정해진 양식(표·문서), 파일 첨부" | 자유롭게 쓴 글(정해진 양식 없음) |

**다른 요구 항목과의 경계**
- 입력 vs 트리거(자율 루프): 트리거는 언제 시작하는지(시점)이고, 입력은 시작할 때 무엇을 받는지(내용물)다.
- 입력 vs 지식베이스: 입력은 이번 한 건을 처리하려고 그때 들어오는 자료이고, 지식베이스는 미리 갖춰 두고 여러 건에 걸쳐 계속 참고하는 판단 근거다.

**앞에서 답해야 하는 것(의존)**: 목표(무엇을 만들어야 하는지 알아야 무엇이 입력으로 필요한지 정할 수 있다).

## 9. 출력

**이름과 정의**: 출력은 에이전트가 만든 결과물을 어디로 어떤 모습으로 내보내는지, 그 결과를 받는 시스템까지 포함한 명세다.

**무엇을 정하는가**: 결과물이 도착할 곳(화면, 이메일함, 파일, 다른 시스템)과 그 도착지가 결과물을 어떤 모습으로 받아들이는지(마크다운을 꾸며 주는지, 글자 그대로 보여주는지), 저장한다면 어느 자리에 저장하는지를 정한다.

**질문 목록**
| 확인할 것 | 무엇을 묻나 | 질문 문구 예시 | 모르겠어요 기본값 |
|---|---|---|---|
| 출력 대상 | 결과물이 어디로 가는지 | "만든 결과물이 어디로 가나요? 예: 화면에 바로 보여준다, 이메일로 보낸다, 파일로 저장한다, 다른 시스템(워드프레스 등)에 올린다" | 화면에 바로 보여준다 |
| 출력 모습(렌더링) | 받는 화면이 꾸밈을 살려주는지, 글자 그대로 보여주는지 | "그 결과물을 받는 화면이 굵은 글씨·표 같은 꾸밈을 알아서 살려주나요, 아니면 쓴 글자 그대로 보여주나요? 예: 워드프레스는 꾸밈을 살려준다, 카카오톡 메시지는 글자 그대로 보인다" | 글자 그대로 보여준다고 가정하고 꾸밈 문법을 쓰지 않는다 |
| 저장 자리(조건부, 있다면) | 저장할 파일 이름·항목 이름이 정해져 있는지 | "결과를 어딘가에 저장한다면, 그 저장 자리(파일 이름·항목 이름)가 이미 정해져 있나요? 있다면 그 이름과 뜻을 알려주세요" | 해당 없음(저장하지 않거나 새로 정한다) |

**다른 요구 항목과의 경계**
- 출력 vs 도구: 위 「5. 도구」 참조.
- 출력 vs 목표: 목표는 무엇을 만들어야 하는지(결과물 정의)이고, 출력은 그렇게 만든 결과물을 어디로 내보내는지다.

**앞에서 답해야 하는 것(의존)**: 목표(결과물 정의를 알아야 그것을 어디로 보낼지 정할 수 있다), 사용자 층(누가 보는 화면인지에 따라 출력 모습이 달라진다).

**산출물**: `plan.md` §3b 입력·출력 절(핵심값 — 출력 대상·모습·저장 자리) + §4 출력 대상 시스템 명세(외부로 나가는 산출물이 있으면 상세 필수), Phase 1 산출물 📡출력 대상 시스템 명세, Phase 5 체크리스트 항목 9(실패 모드에 출력 실패 포함 가능).

## 자료 우선 절차

> 4라운드 토론 쟁점 Q2·Q3("자료를 준 만큼 왜 다시 묻나", "추정값을 어떻게 확인받나") 반영. 사용자가 처음 준 한 줄·자료·원자재로 먼저 채울 수 있는 것을 채우고, 남는 것만 위 순서표대로 1문1답으로 묻는다. 아래 6단계로 진행한다.

**4단 표시** — 요구 항목·확인할 것마다 다음 넷 중 하나로 상태를 남긴다:

| 표시 | 뜻 | 조건 |
|---|---|---|
| **확정** | 사용자가 직접 말했다 | 사용자 원문을 그대로 인용할 수 있을 때만 붙인다 |
| **추정** | 자료를 읽고 에신이 판단했다 | 자료의 출처 구절을 인용할 수 있을 때만 붙인다. 인용할 구절이 없으면 추정이 아니라 생성이다 |
| **생성** | 자료에 없어 에신이 짐작했다 | 출처 구절이 없는 채움은 전부 생성이다. 개별 확인 대상 |
| **미상** | 자료·이전 답 어디에도 없다 | 빈칸으로 두고 순서표대로 질문한다 |

**진행 6단계**:
1. 첫 질문(docs/10 §첫 질문)에서 한 줄 요청과 함께 자료·원자재를 받는다.
2. 받은 자료·원자재로 12개 요구 항목·최대 29개 확인할 것의 초안을 채우고, 항목마다 위 4단 표시를 남긴다.
3. **반드시 묻는 9개**(운영 규칙 1, 비가역 도구가 있으면 10번째 결속 필드 포함)는 상태와 무관하게 사용자에게 확인한다. 다만 자료에 값이 있으면(확정·추정) 처음부터 묻지 않고 "자료엔 ○○로 보이는데 맞나요?" 확인형으로 축약한다.
4. 미상으로 남은 확인할 것은 순서표(위) 순서 그대로 1문1답으로 묻는다.
5. 추정은 요약 1회 확인으로 처리한다 — 원문 발췌를 보여주며 "자료를 보니 ○○로 보이는데, 맞으면 다음으로 넘어가겠습니다"라고 묻되, 고위험 항목(비용·보안·도메인 가드)은 요약 확인에 섞지 않고 3단계의 개별 확인으로 뺀다. 생성은 예외 없이 항목마다 개별 확인한다.
6. 진행 결과를 coverage 표에 남긴다 — docs/10 §Phase 1 원칙 5(coverage 표)의 대상을 "기존 transcript·승인된 MBO·선행 에이전트 문서"에서 **이번에 사용자가 처음 준 자료·원자재까지 포함**하도록 넓힌다. 표는 확인할 것 29행 × 4단 표시 칸으로 두고 Phase 2 목표서 승인 때 함께 보여준다. ★V4.12 표의 **맨 앞에 선행 행 「비가역 도구 유무(게시·삭제·결제·전송)」**를 둔다 — 예/아니오를 먼저 채우고, 「아니오」면 10번째(결속 필드)는 `해당없음`, 「예」면 위 닫힌 목록 전 칸을 묻는다. 닫힌 목록의 「그 외 결과를 바꾸는 값」 칸은 비면 「없음」이라고 적는다(빈칸 금지).

⚠️ 자료 우선은 "생략"이 아니라 "축약 확인"이다. 반드시 묻는 9개(+비가역 도구가 있으면 10번째)·고위험 항목은 자료에 값이 있어도 사용자 확인 없이 그대로 채택하지 않는다.

## 운영 규칙

1. **반드시 묻는 9개** — 목표(#1 결과물 정의·#2 완료 조건), 안전 체계(#22 비용 한도 1회·#23 비용 한도 월 누적·#24 종료 조건·#25 실패 시 처리·#26 보안 개인정보·#27 보안 보관 기간·#28 도메인 가드)는 자료에 값이 있어도 건너뛰지 않고 반드시 사용자에게 확인한다. 자료에 값이 없으면(미상) 순서표대로 1문1답으로 묻고, 값이 있으면(확정·추정) "자료엔 ○○로 보이는데 맞나요?" 확인형으로 축약해서 묻는다 — 묻는 행위 자체를 생략하지 않는다.
   **★V4.12 10번째 — 비가역 도구가 있을 때만 발동(「결속 필드」).** 비가역 도구(게시·삭제·결제·전송)가 하나라도 있으면 위 9개에 더해 10번째로 **「승인·한도가 무엇에 묶이는가」**를 반드시 묻는다. 없으면 10번째는 `해당없음`으로 기록한다(Phase 1 coverage 표 선행 행, 아래 자료 우선 절차 6단계). 이 10번째도 9개와 같이 자료에 값이 있으면 확인형으로 축약해 묻는다(축약 확인 대상). **열린 질문으로 묻지 않고 아래 닫힌 목록을 하나씩 읽어 주며 묻는다** — 열린 질문이면 작성자·사용자가 떠올린 것만 나와 빠지는 필드가 생긴다(실사고: 승인 해시에서 발신자·답장 주소가 빠진 채 출하).
   - 닫힌 목록(메일 예시 용어): ① 발신자 ② 수신자 ③ 답장 주소(reply_to) ④ 참조·숨은참조 ⑤ 제목 ⑥ 본문 ⑦ 첨부 ⑧ 헤더 ⑨ 대상 계정(API 키) ⑩ 설정·환경변수 출처(프로필·설정 화면·`.env`·기본값이 어디서 오는가) ⑪ **그 외 결과를 바꾸는 값** 1칸 — 비면 빈칸이 아니라 「없음」이라고 명시한다. 메일 아닌 도구(게시·삭제·결제)는 같은 질문을 도구 용어로 바꿔 묻는다(대상 계정·대상 위치·금액·옵션 등).
   - 각 필드마다 ⓐ 승인에 묶이는가 ⓑ 값의 출처(코드 상수·설정·환경변수·초안) ⓒ 바뀌면 승인이 무효화되는가를 답받는다. 용어 대응(`docs/30` 비가역 primitive 필드명 ↔ 메일 용어): actor=발신자 · destination=수신자·답장 주소·참조/숨은참조 · artifact(전체 SHA-256)=제목·본문·첨부·헤더 · scope=대상 계정(API 키)·설정/환경변수 출처·그 외 값.
2. 저위험 확인할 것 3개(저장 자리 9번·폴백 LLM 순서 20번·동시성·재시도·재개 정책 16번)는 자료로 확정·추정되면 규칙 4·자료 우선 절차를 따르고(확정은 건너뜀, 추정은 요약 확인), 미상일 때만 기본값을 먼저 제시하는 확인형으로 묻는다. (규칙 1의 9개·★V4.12 10번째와 겹치지 않는 별도 집합)
3. 안전 체계(22~28번)는 3그룹으로 나눠 전달한다: ① 비용(22·23번) ② 종료·실패(24·25번) ③ 보안·도메인 가드(26·27·28번). 그룹 안에서도 확인할 것은 1문1답으로 답을 받는다.
4. 사용자가 순서를 벗어나 먼저 답해 버린 항목, 또는 자료 우선 절차에서 **확정**으로 표시된 항목은 즉시 기록하고, 순서표에서 해당 확인할 것은 건너뛴다(자료 우선 절차의 4단 표시 중 확정 처리와 같다 — §자료 우선 절차 2·4단계 참조). **단, 반드시 묻는 9개(규칙 1, 비가역 도구가 있으면 10번째 포함)는 확정으로 표시됐어도 건너뛰지 않고 규칙 1의 축약 확인("자료엔 ○○로 보이는데 맞나요?")을 거친다** — 이 항목에서는 규칙 1이 우선한다.
5. 진행률 표시는 29개 확인할 것 단위가 아니라 12개 요구 항목 단위로 보여준다(예: "12개 요구 항목 중 5개 요구 항목 완료").
6. 재확인 지점(페르소나·LLM O/X)은 위 순서표에 없는 별도 단계다. 29번 뒤에 온다.
7. 응답 속도(성능) 한도는 질문에서 빼고 코드 기본값(자율 루프 동시성·timeout 쪽)으로 처리한다.
8. 질문 순서(위 표, Phase 1 문답용)와 정의 순서(가이드·SKILL.md·docs/00 설명용, 목표→페르소나→LLM→지식베이스→도구→안전 체계→자율 루프)는 서로 다른 목적이라 분리한다. 가이드의 정의 순서는 이번 재구성으로 바꾸지 않는다.
9. **질문 개수는 대외에 공식·숫자로 말하지 않는다.** 영상·가이드 첫 안내 등 사용자 접점에서 "12개", "최대 29개" 같은 숫자를 확정치로 제시하지 않는다("상황에 따라 필요한 것만 여쭤봅니다" 정도로 설명). 숫자는 이 정의서·docs/10 등 스킬 내부 문서와 가이드 심화 접이식 안에서만 쓴다.
