## Phase 0. 시동 (Intake)

### Phase 0-0. 의존 스킬 확인 — mbo-천상 자동 설치·연결 (★V3.22 신설, 매 실행 자동)

이 스킬은 **`mbo-천상`(공개명 `mbo-skill`, 호출 `/mbo`)에 필수 의존**한다 — Phase 2 목표서·승인·MBO 파일 저장·Phase 8 결과 보고가 전부 거기서 온다. 착수 전 반드시 확인한다.

```
1. 탐지: ~/.claude/skills/mbo-천상/SKILL.md 또는 ~/.claude/skills/mbo/SKILL.md 존재?
   → 있으면 3(검증)으로 — 있다고 건너뛰지 않는다(이전 실행이 404 HTML·절단 파일을 남겼을 수 있음)
2. 없으면 자동 설치 (PO에게 1줄 고지 후 실행):
   Git Bash / macOS / Linux:
     mkdir -p ~/.claude/skills/mbo
     curl -fsSL -o ~/.claude/skills/mbo/SKILL.md https://raw.githubusercontent.com/SUNWOONGKYU/mbo-skill/main/SKILL.md
   Windows PowerShell 5.1 (curl은 Invoke-WebRequest 별칭이므로 curl.exe 또는 아래 명령):
     New-Item -ItemType Directory -Force "$HOME\.claude\skills\mbo" | Out-Null
     Invoke-WebRequest -Uri https://raw.githubusercontent.com/SUNWOONGKYU/mbo-skill/main/SKILL.md -OutFile "$HOME\.claude\skills\mbo\SKILL.md"
3. 검증: 파일 존재 + 첫 줄 '---' + 본문에 'MBO_SPEC_VERSION' 마커 있음. 하나라도 아니면 — `mbo/`(자동 설치본)이면 그 파일을 삭제하고 2로 회귀(1회만), 두 번째도 실패면 5; `mbo-천상/`(운영자 원본)이면 삭제하지 않고 바로 5(수동 확인 안내)
4. 연결: Skill 도구 목록에 /mbo-천상 또는 /mbo 가 보이면 그걸로 호출.
   안 보이면(세션 시작 후 설치라 미등록) → 그 SKILL.md 를 Read 로 읽어 절차를 그대로 수행. 재시작 요구하지 않는다.
5. 실패(네트워크 차단 등) → Phase 2 진입 금지. PO에게 수동 설치 안내:
   https://github.com/SUNWOONGKYU/mbo-skill
```

운영 환경(`mbo-천상` 설치됨)에서는 1에서 발견 → 2 건너뛰고 3(검증)만 수행. 공개본·운영본이 같은 절차 하나로 동작한다.

- 인자가 있으면 그것을 제조 대상으로 한다.
- 인자가 없으면 대화 맥락에서 "무슨 에이전트를 원하는지 + 구동 방식(웹사이트형/데스크톱형) + 모드(단일/배치/포털)"를 도출한다.
- 도출 불가 시 PO에게 한 줄 질문으로 확인한다.
- ★V3.25 **원자재 질문(필수)**: "이 에이전트를 만들 때 쓸 원자재(선행 에이전트·코드·문서)를 직접 가져오셨습니까? 있으면 경로를 알려주세요." — 있으면 **발굴 경로 A**(그것만), 없으면 **경로 B**(공개 발굴). 답을 MBO 「제조 대상」 메타에 `발굴 경로` 행으로 적는다.

### ★V3.14 신설, ★V3.19 용어 체계 확정 — 역할 고정 가드 (착수 전 자기 선언)

**용어 체계 (★V3.19, PO 확정)** — 이 공장 전체를 관통하는 4개 층위:

| 용어 | 뜻 |
|---|---|
| **지휘자** | PO — 무엇을 만들지 지시하고 결과를 승인하는 사람 |
| **시스템구축자** | Claude Code(나) — 에이전트를 만드는 쪽. 아래 "제조자"와 동의어 |
| **State Machine** | **판단 없이** "다음에 뭘 실행할지"만 결정론적 조건(파일 존재·mtime·상태값 등)으로 정하는 무판단 스케줄러/뼈대. 반복 제어·액션 화이트리스트·confirm 관문 등 집행·게이트 담당 |
| **액션봇** | 에이전트 안에서 **판단하는** 쪽 — LLM. State Machine이 호출하는 각 단계 안에서 실제 추론(질문 생성·검증·평가 등)을 한다. 대화(플로팅 위젯 등)로 사용자가 만나는 창구는 이 판단 주체에게 열린 문이다 |

**★V3.20 정정 — 자율 루프 = State Machine 단독이 아니라 State Machine과 액션봇의 합작이다.** State Machine(무판단 스케줄러)이 "다음 단계"를 결정론적으로 고르지만, 그렇게 호출된 단계들(질문 생성·검증·평가 등) 내부에서는 액션봇(LLM)이 실제로 판단한다. State Machine만 있으면 그냥 고정 스크립트(자율성 없음), 액션봇만 있으면 경계 없는 폭주(안전 체계 붕괴) — **자율 루프는 이 둘이 맞물려야만 성립**한다. 두 활동 주체 구분 자체는 배포유형과 무관하게 모든 에이전트에 보편 적용된다. 단, **액션봇을 "플로팅 UI 위젯"으로 구현하는 방식은 데스크톱형 전용**이다(§「`ui/index.html` 필수 요건 9」) — 웹사이트형은 페이지 자체가 이미 액션봇 창구라 띄울 필요가 없다.

착수 전에 스스로 확인: **"나는 지금부터 [에이전트명]을 만드는 시스템구축자다. [에이전트명](액션봇+State Machine)이 아니다."** 이 선언이 형식적으로 끝나지 않도록 아래 두 지점에서 재확인한다.

- **Phase 1 문답 중** — PO가 도메인 예시를 주면(예: "이런 계약서를 검토해줘") 그 예시로 실제 검토 결과를 만들어 답하지 않는다. 예시는 에이전트가 나중에 처리할 **입력 샘플**로만 다룬다. "이 샘플로 제가 지금 검토해드릴까요, 아니면 이런 샘플을 처리할 에이전트를 만들어드릴까요?"가 헷갈리면 PO에게 확인한다.
- **Phase 6 조립 중** — 매 산출물 저장 직전 자문: "이 파일이 에이전트 자산(system_prompt·engine.py·SKILL.md·도구 배선)인가, 도메인 결과물(분석·보고서·완성된 글)인가?" 후자를 저장하려는 순간이면 역할이 무너진 것 — 멈추고 그 도메인 결과물을 만들어낼 절차를 코드/프롬프트로 옮긴다.
- **탐지 신호**: 작업 폴더에 도메인 결과물 파일만 늘어나고 `system_prompt`·`engine.py`·`SKILL.md` 등 에이전트 자산 파일 수가 늘지 않는다 — 이러면 지금 에이전트가 아니라 그 에이전트가 할 일을 대신 하고 있는 것이다.

### ⚡ 라이트 분기 게이트 — Q-Lite (V3.8 신설, 구동 방식/모드 판별보다 먼저)

**본체 에신은 방대하다.** 만들 대상이 "가볍고 단순한 단일 에이전트"면 경량판 `/에신-라이트`로 라우팅해 빠르게 출하한다. Q-구동방식/모드 판별 전에 먼저 판정.

```
Q-Lite. 다음이 모두 YES인가?
  ① 에이전트 1개(배치 아님) · ② 포털 불필요 · ③ 외부 부품 거의 없음(기본 LLM 위주, 검증 부품 ≤2)
  · ④ 단일 도메인(다도메인 고위험 아님) · ⑤ 단발 또는 단순 반복(복잡 자율루프 아님)
    모두 YES → 🟢 /에신-라이트 로 라우팅 권고 (3~5라운드 문답 → 간이 제조)
    하나라도 NO → 본체 에신 계속 (아래 Q-구동방식으로)
```

- 라이트로 가도 **핵심 안전장치(고위험 면책 가드·보안·비용한도·PO 승인 게이트·실호출 검증·자기검증 회피)는 동일하게 유지**된다 — 압축은 문답·리서치·BOM·QC 라운드 수에만 적용.
- 라이트로 시작했다가 복잡도가 올라가면(부품 3개+·포털/배치·다도메인 고위험) 라이트가 **본체 에신으로 에스컬레이션**한다(에신-라이트 SKILL의 에스컬레이션 규칙).
- PO가 "그냥 본체로 풀로 해"라고 하면 라이트 권고를 무시하고 본체 진행.

### 구동 방식 판별 — Q-구동방식 (V3.2 신설, ★V4.4 "인프라 A/B" 명칭 폐지) ★ 모드 판별보다 먼저

| 신호 | 구동 방식 |
|------|--------|
| "Supabase 있어" / "사내 포털" / "운영 엔진 + DB" / "Vercel 배포" | **웹사이트형 — Supabase 있음** |
| "내 PC만" / "DB 없음" / "USB 배포" / "내부망 공유 폴더" / 인터넷 안 됨 | **데스크톱형 — DB 없음 (로컬 .py)** — LLM은 PO 본인용이면 `claude` CLI(구독) 기본, 배포용일 때만 API 키 (💳 원칙) |

**판별 불가 시 Q-구동방식**:
```
Q. 다중 사용자가 웹 브라우저로 접속하는 호스팅 인프라(Supabase·Vercel·인증 DB)가 있는가?
    YES → 웹사이트형 — Supabase 있음 (운영 엔진 api/run.py 사용)
    NO  → 데스크톱형 — DB 없음 (로컬 .py, 분리형 — engine.py + skills/*.md + run.py)
           · LLM: 로컬 = claude CLI(작업·1차) → codex CLI(2차·폴백) / 웹사이트형 = API 키 (💳 원칙)
```

**구동 방식 → 모드 → 산출물 결정 트리 ★V3.5 후속 신설 (Medium 4)**

```
                  ┌────────────────────────┐
                  │  PO 요청 한 줄 도착     │
                  └────────────┬───────────┘
                               │

                  │ Q-구동방식: Supabase·  │
                  │ Vercel·DB 호스팅 있나? │

                YES     │             │     NO
                        ▼             ▼
        ┌─────────────────┐    ┌──────────────────┐

                 │                       │
   ┌─────────────┼──────────┐            ├─────────────┐
   ▼             ▼          ▼            ▼             ▼
 단일 1a      배치 1b    포털 1c       단일 1a      배치 1b
   │             │          │            │             │
   ▼             ▼          ▼            ▼             ▼
```

**구동 방식이 모드를 제약한다**:

| 구동 방식 | 가능 모드 | 불가 모드 |
|:-:|---|---|
| **웹사이트형** (Supabase 있음) | 단일 / 배치 / 포털 모두 가능 | — |
| **데스크톱형** (DB 없음) | 단일 / 배치 | **포털 ❌** (인증·DB 필수) |

**왜 분리형이 데스크톱형의 표준인가**: 웹사이트형↔데스크톱형 간 자산 이동을 무비용으로 만들기 위함. SSOT는 `스킬스/{AGENT_ID}_{skill_id}/SKILL.md` 단일 — 웹사이트형 환경에서는 Supabase에 sync, 데스크톱형 환경에서는 로컬 engine.py가 같은 파일을 직접 읽음. **에이전트가 처음엔 데스크톱형으로 시작했다가 사용자 늘면 웹사이트형으로 승격하기가 0 변경으로 가능.**

### 모드 판별 (V3.0 신설, V3.1 결정 트리 강화)

**1단계 — 키워드 신호 (1차 후보)**

| 신호 | 모드 |
|------|------|
| "~하는 AI 만들어줘" / 1건 / 단일 사용처 | **단일 모드** (Phase 1a) |
| "N개 묶음" / "한 직능 전부" / "표준 템플릿" / 카탈로그 존재 | **배치 모드** (Phase 1b) |
| "포털" / "허브" / "1 호스팅 = N 에이전트" / 카탈로그 + 인증 + 관리 콘솔 | **포털 모드** (Phase 1c) |

**2단계 — 키워드만으로 판별 불가 시 결정 트리 (V3.1 강제)**

신호어가 모호하거나 PO가 "단일이야"로 강하게 우긴다 해도 다음 3개 질문에 답해 모드를 재판정:

```
Q1. 만들 에이전트 수가 2개 이상인가?
    NO  → 단일 (Phase 1a)
    YES → Q2

Q2. 호스팅이 1개로 공유되는가? (같은 도메인·같은 인증)
    NO  → 배치 (Phase 1b) — 독립 호스팅 N개
    YES → Q3

Q3. 공통 인증·페이지 구조·관리자 콘솔이 필요한가?
    NO  → 배치 (Phase 1b) — 단순 일괄 제작
    YES → 포털 (Phase 1c) — 화면부(6-P)·공통부(6-C) 별도 단계 필요
```

**3단계 — PO 강제 거부권 (V3.1 신설)**

PO가 결정 트리 결과에 동의하지 않고 "단일로 가자"고 우길 경우 — 그래도 진행은 가능하나 출하 보고서에 다음을 명시한다:
- `mode_override: true`
- `tree_recommended: {배치/포털}`
- `po_decision: 단일`
- `risk: V2.0과 같은 우회 사고 재발 가능` (경고 의무 기록)

이 경고가 있는 상태에서 Phase 9 운영 루프에 진입한 뒤 회귀 트리거(에러율·피드백)가 발동되면 **모드 재선언부터** 다시 시작한다.

모드를 명확히 선언하지 않으면 V2.0처럼 통째 우회되는 사고가 재발하므로, **인자/맥락에서 자동 판별이 안 되면 결정 트리를 반드시 수행하고 결과를 PO에게 확인한다.**

### ★ V3.5 핵심 원칙 — 질문은 AI가 한다 + 초보자 친화

1. **묻는 주체는 AI(스킬)이다.** PO에게 항목 나열을 던져 일방적으로 답하라고 시키지 않는다. AI가 한 질문씩 던지고 → PO가 답하고 → 다음 질문. 1문1답 진행.
2. **초보자도 답할 수 있는 질문이어야 한다.** 기술 용어를 그대로 쓰지 말고 **풀어쓴 뒤 예시 1~2개**를 동반한다.
3. **객관식·예시형 우선.** 가능하면 `AskUserQuestion` 도구로 2~4개 선택지 + "Other" 직접 입력 형태. 자유 서술은 정말 자유 답이 필요할 때만.
4. **10라운드 기본, 부족 시 추가.** 종료 신호(아래)가 안 나오면 라운드를 늘려 보강한다. 절대 채우지 못한 채 Phase 2로 넘어가지 않는다.
5. **★V3.12 이미 답이 있는 질문은 하지 않는다.** 착수 전에 **발굴 항목 coverage 표**를 먼저 채운다 — 기존 transcript·승인된 MBO·선행 에이전트 문서에서 이미 확정된 항목을 표시하고, **비어 있는 항목만 질문**한다. 단축한 결과(무엇을 왜 건너뛰었는지)는 PO 승인을 받는다. 암묵적 요구 누락은 이 표로 통제한다.
6. **★V3.12 실행 토폴로지를 반드시 가른다.** **작업팀 편제(제조에 투입하는 사람·에이전트 수)**와 **제품 런타임 동시성(에이전트가 동시에 처리하는 작업 수)**은 다른 값이다. 섞이면 정원과 처리량이 잘못 구현된다. 제품 쪽은 `병렬도 · 큐 · timeout · 재시도 · 재개 정책`을 필수 명세로 받는다(단일 실행이면 기본값 제시로 갈음).

### Phase 1b — 배치 모드 (5라운드 공통 + 변주)

N개 에이전트를 1개씩 돌리는 건 비현실적이므로 **공통 + 변주** 구조로 진행한다:

| 단계 | 라운드 | 발굴 대상 |
|------|:---:|----------|
| **공통 10라운드 + α 문답** | 1~5 | 카테고리 공통 — 도메인(직능)·공통 트리거·공통 입력/출력·공통 제약·공통 구현 7요소·★출력 대상 시스템 공통★·**공통 분류**(R10 — 카테고리가 하나의 유형이면 공통, 섞이면 변주에서) |
| **개별 변주** | 6~N | 에이전트별 차이점만 짧게 — 🎯**개별 목표**·🏷️**개별 이름**·📂**개별 분류**(공통과 다르면) 필수 명시 |
| **카탈로그 수립** | 종합 | N개를 표 1장으로 정리 (코드·이름·**유형 분류**·차이점·우선순위) |

배치 모드 첫 멘트:

### Phase 1c — 포털 모드 (4+3+N, 웹사이트형 강제)

⚠️ **웹사이트형 필수.** 포털 모드는 다중 사용자·인증·세션·과금 DB가 본질이므로 데스크톱형(DB 없음) 환경에서는 구현 불가. Phase 0의 Q-구동방식이 데스크톱형이었다면 **포털 모드 자동 차단** → 1a(단일) 또는 1b(배치)로 강제 회귀.

선택지 (데스크톱형 + 포털 요청 시):
1. 웹사이트형으로 승격 (Supabase 도입) → 그 후 포털 가능
2. 1b 배치로 회귀 — 같은 폴더에 N개 도구 모음으로 제조 (인증 없음)

1 호스팅 = N 에이전트 = 화면부(6-P)·공통부(6-C)가 필수. 다음 3개 묶음을 순차적으로 10라운드 + α 문답:

| 묶음 | 라운드 | 발굴 대상 |
|------|:---:|----------|
| **① 호스팅 화면부** | 1~4 | 인증 정책·페이지 구조·헤더·관리자 콘솔·도메인·배포 |
| **② 공통부** | 5~7 | 비용 가드·세션·도구 round-trip·면책·첨부·로깅·피드백·★LLM 폴백 체인★ |
| **③ 에이전트 카탈로그** | 8~N | N개 에이전트 목록 — Phase 1b의 공통/개별 변주 적용 |

포털 모드 첫 멘트:
> *"포털 모드 — 1 호스팅에 N개 에이전트를 진열합니다. 호스팅 화면부(4라운드) → 공통부(3라운드) → 에이전트 카탈로그 순으로 한 질문씩 드립니다."*

### 종료 신호 / 금지

- **종료 신호**: 모드별 산출물(아래)이 모두 채워진 시점. PO가 *"이건 내가 던졌어도 못 만들었을 질문"*이라 느끼는 라운드가 누적되면 깊이 충분.
- **부족 신호 → 라운드 추가**: 산출물 항목 중 비어 있는 게 있거나 PO 답변이 "잘 모르겠다"·"적당히"로 끝났으면 **그 항목만 짚어 1~3 라운드 추가 질문**. 10라운드 채웠다는 이유로 강제 종료 금지.
- **금지**: 라운드 중간에 *"바로 답 줘"*로 건너뛰지 않는다 — 막연한 스펙으로 회귀한다.

- 경로 A 원자재의 라이선스 판정은 「재사용 증거·라이선스 게이트」 그대로(PO 소유 확인 / 공개 코드 LICENSE / 불명은 패턴만).
- 실습·교육에서는 경로 A가 기본이다(90분 내 완주 목적) — 리서치·발굴을 빼고 「분해 → 도메인 교체 → 조립 → 실행 확인」에 시간을 쓴다.
- **경로 A 「도메인 교체」 치환 목록(빠뜨리면 V1 이 잡는다 — 실측 2026-09-17)**: ① 에이전트 이름(헤더·`<title>`·README·CLAUDE.md·시작.bat 창 제목) ② 포트(`ui.py PORT` 와 **매뉴얼·README 의 포트 숫자·「Port N is already in use」 문구까지**) ③ 외부 호출 식별자(`cite.py` 등의 `UA` 문자열 — 원자재 이름이 남으면 안 됨) ④ README·CLAUDE.md 가 가리키는 파일(대조표·보고서·시운전 산출물)은 **실제로 만든 것만** 남긴다 — 원자재에 있던 파일 참조를 그대로 두면 죽은 링크 ⑤ 도메인 어휘(버튼·단계명·안내문). 치환 뒤 `grep -rn "{원자재 이름}|{원자재 포트}"` 로 0건 확인이 조립 완료 조건.

이미 잘 만들어진 것을 찾는다. 시간은 PO만이 만들 수 있는 부분에 쓴다. (아래 카탈로그는 **경로 B**에만 적용)
(출처: SUNNY AI MAGIC 50 #38 도구 발굴 / find-skills-기본)

> ★V3.12 **부품을 실제로 복사·재단하려면** 「재사용 증거·라이선스 게이트」 절을 먼저 통과해야 한다 — 라이선스 두 경로 판정 · 벤치마크 입고 카드 · 코드 포렌식 · 재사용 원장. 패턴만 참고할 때는 해당 없음.

## ★V3.12 신설 — 재사용 증거·라이선스 게이트 (Phase 3~4 필수)

> 부품을 가져오면 **출처·권리·검증을 함께 가져온다.** 코드만 복사하면 원래 보장하던 것이 사라진다.

### 1) 라이선스 판정 — 두 경로로 가른다 (섞지 마라)

| 유래 | 판정 방법 | 통과 시 |
|---|---|---|
| **공개 코드** | LICENSE·NOTICE·저장소 이력으로 확인. 불명이면 🔴 컷 | 복사·재단 가능(고지 의무 이행) |
| **PO 소유 내부 자산** | 파일 안에 LICENSE가 없어도 **PO 소유 확인으로 판정**. 자산명·확인자·확인일을 재사용 기록에 고정 | 복사·재단 가능 |
| **유래 불명** | 어느 쪽도 확인 안 됨 | **패턴 참고만** — 코드 복사 금지, 재구현 |

⚠️ 파일에 라이선스 문서가 없다는 이유만으로 내부 자산을 외부 불명 코드로 오판하지 마라. 반대로 구두 소유권 확인을 다른 자산까지 확대 적용하지 마라.

### 2) 벤치마크 입고 카드 (내부 자산·선행 구현을 부품으로 쓸 때)

PO가 지정한 선행 에이전트는 "구조 참고"가 아니라 **코드 공급원**으로 다룬다. 부품마다 기록:

`원본 경로 · 소유권 · 라이선스 판정 · 파일과 심볼 · 원본 해시 · 적용 위치 · 수정 내역 · 대응 테스트`

### 3) 재사용 증거 원장 (실제 재사용·의존성이 있을 때만 강제)

- `SOURCE_REUSE_LOG.md` — 무엇을 어디서 가져와 어디에 넣었는지, 버전·커밋·해시
- `THIRD_PARTY_NOTICES.md` — 외부 라이선스 고지

없으면 취약 버전 교체·회귀 원인 추적·저작권 감사가 불가능하다.

### 4) 코드 포렌식 (PO 지정 후보와 고득점 후보에 적용)

순서대로 검사: **파일 크기 → generated/vendor/backup 제외 → 진입점 → 호출 관계 → 의존성 → 테스트 → 보안 경계**
거대 파일(수십만 바이트 단일 파일)·`.bak`·도메인 결합 코드를 그대로 복제하면 기존 결함까지 승계된다.

### 5) 회귀 테스트 승계표

부품마다 `원본이 보장하던 행동 → 원본 테스트 → 우리 쪽 대응 테스트 → 실제 호출 증거`를 연결한다.
**코드 재사용이 검증 재사용으로 이어져야** 한다. 중복은 행동 계약 단위로 통합.

### 6) 벤치마크 정보구조 계층 보존 게이트

벤치마크의 화면·기능을 가져올 때 **상위 분류를 빼먹고 하위 항목만 옮기지 마라.**
적용 전 `원본 영역 → 상위 분류 → 하위 항목 → 상태 → 상세 행동` 계층표를 만들고, GUI·API·테스트에 각 계층이 남았는지 coverage로 확인한다. 의도적 생략은 사유와 PO 승인을 기록. 연결되지 않은 경로는 삭제하지 말고 **미연결로 표시**한다.

### 7) 필수 보조 스킬의 배포 방식 확정

의존하는 보조 스킬마다 MBO에서 **전역 참조 / 에이전트 로컬 번들 / 패키지 의존** 중 하나를 확정한다.
독립 에이전트는 로컬 사본의 **버전·파일 수·해시**를 기록하고 런타임 탐색 우선순위를 명시한다. 전역 설치 여부만 확인하면 다른 PC에서 기능이 통째로 사라진다. healthcheck에서 원본과의 해시 불일치를 알린다.

## skill-create와의 관계 (V3.0 — 양방향 명시, V3.5 후속 — 경계 표 강화)

`/skill-create`는 형제 공장이다. 같은 9-Phase 방식·같은 분해·검증 후 조립 철학을 공유한다.

### ★ 두 공장 경계 — 어느 쪽으로 가야 하나? (V3.5 후속 신설)

| 차원 | `/skill-create` | `/llm-dependent-agent-create` (이 공장) |
|---|---|---|
| **제조 산출물** | `~/.claude/skills/{name}/SKILL.md` (마크다운) | 운영 가능한 에이전트 자산 (코드·UI·DB·인프라) |
| **실행 주체** | Claude Code가 컨텍스트에 SKILL.md를 주입해 실행 | LLM API + 엔진 코드 + 사용자 인터페이스 |
| **사용 위치** | 개발자 본인의 Claude Code 세션 | 외부 사용자가 호출하는 서비스 |
| **DB·호스팅** | 없음 (마크다운만, 로컬 폴더) | 웹사이트형 (Supabase) 또는 데스크톱형 (.py + .env). 호스팅 Vercel·Cloud Run·로컬 PC 등 |
| **모드** | 단일 / 배치 (포털 불가) | 단일 / 배치 / **포털** (1 호스팅 = N 에이전트) |
| **Phase 6 구조** | 단일 — SKILL.md 1장 | 3단 — 실행부(6a) + 화면부(6-P, 포털) + 공통부(6-C, 배치·포털) — 단일 모드는 세 부분을 6a 안에서 함께 조립 |
| **7요소** | 제품 자기완결(SKILL.md 한 장 안에서 완결)·단일 책임 중심 | 7요소 전부 (페르소나·LLM·목표·지식베이스·도구·안전 체계·자율 루프 — 메모리는 지식베이스 하위 작업 지식, 자가평가는 자율 루프 내부 평가) |
| **Phase 7-3+ 사람 눈 검증** | 외부 출력 스킬만 적용 (대다수 면제) | 거의 모든 에이전트 (외부 출력 본질) |

**선택 가이드**: 산출물이 Claude Code 컨텍스트 안에서만 동작하면 → `/skill-create`. 외부 사용자가 호출하는 서비스가 필요하면 → 이 공장.

**양방향 흐름**:
- 에이전트로 출하된 자산이 → Claude Code 스킬 zip으로 **재포장** 가능 (제작자 선행 프로젝트 93개 → 스킬 zip 93개 사례)
- 스킬로 시작된 자산이 → 독립 에이전트로 **분리·출하** 가능

같은 BOM·같은 방법론·다른 포장.
