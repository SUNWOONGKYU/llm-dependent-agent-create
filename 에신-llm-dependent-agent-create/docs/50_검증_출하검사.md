## Phase 7. 출하 검사 — QC 4단 (V3.0)

**자기검증 금지. 검증은 여기서 단 한 번.** 제조에 참여하지 않은 **V1(Claude Code Teammate·Sonnet 5) 1회 → V2(Codex, 폴백 Opus 5 Teammate) 1회 — V2는 L 규모만** 순으로 투입한다 — 「검증 편제」 절. 반려 항목은 수정 후 그 항목만 재확인한다(전체 재라운드 없음).

### 7-0. V1·V2 소환 메커니즘 (V3.1 신설, ★V3.23 — 1회 원칙)

"별도 V1을 투입한다"는 선언만으로는 V2.0처럼 자기검증으로 회귀할 수 있다. 다음 메커니즘을 강제한다:

**소환 절차 (4단계 — 모두 필수)**:

1. **별도 Agent 도구 호출** — V1은 `Agent(subagent_type="general-purpose", model="sonnet", mode="auto")`(Sonnet 5) Teammate로, V2는 Codex CLI(탐지 통과 시) 또는 `model="opus"` Teammate 폴백으로 띄운다. 제조 세션·제조 Subagent가 자기 자신을 검증하지 않는다.
2. **제조 컨텍스트 비전달** — V1 prompt에는 산출물(코드/문서/페이지)과 **검증 기준**만 전달. 제조 과정의 의도·근거·내부 결정 사항은 전달 금지 (편향 차단).
2-1. ★V3.26 **소환 전 스냅샷** — 작성자가 상태 파일·출력물(`state.json`·`history.json`·`output/`)을 `_개발자료/_qc/pre_verify_snapshot/`에 복사한 뒤 소환한다. 검증자가 실수로 지워도 복구 가능해야 한다(실사고 2026-09-17: V1이 intake() 직접 호출로 완성 상태 초기화).
2-2. ★V3.26 **상태 변경 금지 명시** — V1·V2 prompt에 "상태를 바꾸는 함수·라우트·CLI 명령(접수·승인·실행·재작성·설정 변경·초기화) 호출 금지, 순수 함수·읽기 라우트·정적 분석·기존 테스트만" 을 적는다. "읽기전용"이라는 말만으로는 부족하다 — 검증자는 재현하려고 실행 함수를 부른다.
3. **외부 게이트 도구 사용 의무** — 코드 검증은 `node --check`·`py_compile`·`ruff`·`eslint` 등 **외부 도구 실행 결과**를 함께 보고. Subagent의 의견만으로 판정 금지.
4. **호출 증거 기록** — Phase 8 출하 보고서의 "QC 결과" 항목에 `verification_agent_invocations: N` 카운트 + 호출 시각·duration 명시.

**금지**:
- ❌ 제조 Subagent에게 "이제 검증해라"라고 추가 지시 (같은 Subagent의 역할 전환)
- ❌ 메인 Claude Code(SA)가 직접 검증 의견 작성 (자기검증)
- ❌ Subagent 호출은 하지만 prompt에 제조 과정을 다 보여줘서 편향 유도

**위반 시 효과**: QC 결과 무효 처리, Phase 7 처음부터 재실행.

> **★V3.22**: 검증 루브릭·절차는 본문 내장 그대로(외부 스킬 위임 아님). 검증 주체는 「검증 편제 — 작성자 · V1 · V2」 절과 5A-3 Round 루프 참조.

### V1·V2 prompt 양식 ★V3.5 후속 신설 (입력/출력 정의 명문화)

자기검증 편향 차단을 위해 Subagent prompt를 다음 양식으로 통일한다:

**입력 (Subagent에 전달)**:
1. **검증 대상**: 산출물 파일 경로(들) 또는 산출물 텍스트 자체
2. **검증 기준**: 다음 4축 (모든 검증에 공통)
   - ① 사양 반영도 — changelog·기획안·MBO 목표 대비 본문 구현 여부
   - ② cross-file 정합성·자기모순·dead-link
   - ③ 100점 6 루브릭 채점 (사실·용어·구조·규칙·실용 각 15점 + 사양 충족률 25점)
   - ④ 반려 항목 목록 (Critical/High/Medium/Low — 수정 후 그 항목만 재확인)
3. **출력 형식**: 파일별 점수표 + 결함 분류 + 종합 점수 (응답 분량 한도 명시)
4. **★V3.9 필수 입력 — `human_facing` 판정**: Phase 1 발굴 항목 11(🖥️ 사용자 층) 답변값을 그대로 넘긴다. 답변이 **②(일반인·전문직 실무자)** 또는 **④(모르겠어요 → ②로 자동)** 이면 `human_facing: true` — 이 값이 `tools/verify_windows_adapter.ps1`의 `-HumanFacing` 스위치 호출 여부를 결정한다. 이 필드를 양식에서 비워두면 룰 7이 잠들어 GUI 없는 출하가 조용히 통과한다(V3.9가 막으려던 사고) — 양식만 채우면 자동으로 전달되도록 **항상 채운다**.

**전달 금지 (편향 차단)**:
- ❌ 제조 과정·의도·내부 결정 이력
- ❌ 다른 검증자의 평가 점수 (cross-pollution 방지)
- ❌ 제조자(작성자)의 의견·자평
- ❌ "이 부분은 의도된 설계다" 같은 변호 문장

**출력 (Subagent가 메인에 반환)**:
- 파일별 6축 점수표 + 종합 점수
- Critical/High/Medium/Low 결함 목록 (라인 인용)
- 반려 항목(재확인 대상) 목록
- 외부 도구 실행 결과(있다면)

### 규모 판정 → QC 강도

| 규모 | 정량 판정 기준 (V3.1 — AND 조건) | QC 파이프라인 |
|------|----------|--------------|
| **S** | 부품 ≤ 2개 **AND** 코드 라인 ≤ 300 **AND** UI 없음 **AND** 배포형 아님 | 내장 QC 4단 + V1 1회 (V2 없음) |
| **M** | 부품 3~5개 **OR** 코드 라인 301~1500 **OR** UI 있음 (단일 페이지) | 내장 QC 4단 + V1 1회 (V2 없음) |
| **L** | 부품 ≥ 6개 **OR** 코드 라인 > 1500 **OR** 배포형 **OR** 포털 모드 **OR** UI 다수 페이지 | 내장 QC 4단 + V1 1회(2명 병렬 가능) + **V2 1회** |

**경계선 처리**: 두 규모에 걸치면 **높은 쪽으로 판정** (S↔M 경계 → M, M↔L 경계 → L). "딱 3개"·"애매한 UI" 같은 정성적 회피 금지. 배치/포털 모드는 자동 L.

### 4단 QC (V3.0 분해)

모든 규모에 공통 — 다만 강도는 규모별로 차등.

#### 7-1. 정적 분석
- **Dead-link 검사** — `<a>` href 검증, 외부 링크 HEAD 확인
- **`href` 없는 `<Button>`·클릭 가능해 보이는 `<div>` 검출** (SKILL_ATLAS 교훈)
- **JS brace check** — `node --check` 모든 .js 파일
- **Python 컴파일** — `py_compile` 또는 `python -c "import {module}"`
- **시크릿 누출 검사** — `git secrets`·정규식 패턴
- **deprecated API 사용 검사**
- ★V3.12 **Windows 설치 스크립트 인코딩 게이트** — PowerShell 스크립트는 ASCII-only 기본, 한글이 있으면 UTF-8 BOM 저장 확인 + **실제 PowerShell 5.1 파서로 구문 검사**. 정적 내용 검사만으로는 설치 실패를 못 잡는다

#### 7-2. 동적 검증
- **실제 LLM 호출** — ★V3.12 **채택한 런타임 공급자에만** round-trip 1회. 미채택 공급자·폴백 경로는 fake backend로 검증한다(쓰지도 않을 키·비용 때문에 출하가 막히면 안 된다). 폴백을 실제로 채택한 프로젝트만 폴백 실호출을 opt-in
- **도구 round-trip** — 노출된 도구가 실제로 호출되는지
- **데모 모드 폴백** — API 키 없을 때 샘플 출력 동작
- **에러 경로** — 잘못된 입력·타임아웃·API 실패 시 안전한 응답
- ★V3.12 **실행 환경 probe 통과** — 구독 CLI를 쓰면 binary·version·로그인·flag·구조화 출력 지원을 실행 전에 탐지하고 snapshot 기록 (「실행 환경 probe·호출 규격」 절)
- ★V3.12 **구조화 출력 실호출 1회** — 공급자 strict schema(모든 object `additionalProperties:false` + 전체 required, 미지원 format 제거)로 짧은 호출 1회. 단위 테스트 통과는 근거가 아니다
- ★V3.12 **비가역 도구 승인 결속 확인** — 게시·삭제·결제 도구가 있으면 artifact 해시·대상·만료에 승인이 묶였는지, 내용 변경 시 무효화되는지 실제로 시험

#### 7-3+. ★ 출력 대상 시스템 실제 화면 확인 (V3.5 신설 — claude-news-agent 회고)

**제조한 에이전트가 외부 시스템(웹사이트·DB·메신저 등)에 결과물을 게시·저장한다면, 그 시스템의 실제 사용자 화면을 사람 눈으로 확인하기 전까지 Verified 처리 금지.**

- 자기 검증 금지의 구체 적용: `curl 200`, `python --dry-run` 통과, `SELECT * FROM ...` preview 텍스트 확인, 에이전트 자체 self_critique 5/5 — **이 모든 신호의 조합도 사람 눈 화면 확인을 대체하지 않는다**
- 검증 주체: 작성자 또는 제조 Subagent **금지** → PO 직접 또는 V1(→ V2)
- 검증 화면: 출력 대상 시스템에서 **일반 사용자가 보는 그대로의 화면**. (관리자 콘솔의 raw DB 뷰 ≠ 사용자 화면)
- 검증 항목 체크리스트 (최소):
  - 텍스트가 의도한 시각 표현으로 렌더링되는가? (마크다운 `#`·`**` raw 노출 없음)
  - 라벨·배지·아이콘이 의미와 맞게 표시되는가? (예: 외부 링크 라벨이 정확한 도메인 의미와 일치)
  - 클릭 가능한 요소가 실제로 클릭되는가? (SKILL_ATLAS 교훈)
  - 모바일/데스크톱 양쪽에서 깨지지 않는가?
  - **(배치·포털) 콘텐츠 교차오염 0 — 각 에이전트의 설명·태그라인·메타(description·og·twitter·JSON-LD·본문)가 자기 기능과 일치하는가?** 타 에이전트 문구 복붙·생성 템플릿 잔재가 없는가? (실서비스 2026-06-11 회고 — 배치 생성 버그로 보안 에이전트 태그라인이 무관 10개 에이전트 5개 필드에 복제되어 사용자에게 틀린 설명·잘못된 SEO 메타가 노출됨. 표본 몇 개가 정상이어도 전수/표본 확대 점검)

### 7-5. 합격 판정 체계 (★V3.24 — 점수 + 이진 QC 둘 다)

V1·V2는 **점수를 매긴다**(6축 100점) 그리고 **4단 QC는 O/X**로 따로 판정한다. 둘 다 통과해야 출하.

| 축 | 배점 | 무엇을 보나 |
|---|---|---|
| 사실 정확성 | 15 | 코드·문서·**관계도/흐름도 SVG**가 말하는 것이 실제로 그렇게 동작·존재하는가(실행 결과·grep 근거). 흐름도 단계 ↔ 화면 단계 1:1 |
| 용어 일관성 | 15 | 같은 개념에 같은 이름(7대 구성요소·상태값·라우트·파일명) |
| 구조 완성도 | 15 | 7대 구성요소 전부 구현·문서 4종·폴더 표준(GUI 템플릿 9절) |
| 규칙 준수 | 15 | 헌법(한국어·로컬·키 0·자기검증 금지·제약 5)·리서치 함정 7 |
| 실용성 | 15 | 비개발자가 시작.bat→화면→결과까지 막힘 없이 가는가, 오류 문구가 사람 말인가 |
| **사양 충족률** | 25 | MBO 최상위 목표·KPI·산출물 표 대비 실제 구현 비율 |

**합격선(하드 게이트)**: **총점 ≥ 95** AND **Critical·High 결함 0** AND **4단 QC(7-1 정적·7-2 동적·7-3 클릭·7-4 가드 시뮬) 전항 O** AND 사용자 여정 KPI 통과. 하나라도 아니면 불합격.

**불합격 처리(라운드 재발 방지)**: 작성자가 결함을 수정 → 검증자에게 **그 결함 항목만** 재확인 요청 → 검증자는 재채점하지 않고 "소거됨/잔존" 이진으로 답한다. 잔존이면 Phase 6 회귀(구조 문제). 전체 재라운드 없음.

**V1 → V2**: V2는 같은 양식으로 1회 채점. `|V1 − V2| > 3점`이면 V2가 찾은 결함을 수정하고 그 항목만 V2에 재확인. V2가 채점 형식을 못 지키면 `V2 미실시 (사유)` 표기 + V1 점수 최종. Medium·Low는 출하 후 Phase 9 개선 백로그(출하 보고서에 기재).

**혼동 금지**: 이 채점은 *제조 출하 검증*이다. 제품 내부의 자가채점(예: 장별 Likert 루브릭 90점)은 *제품 품질 루프*이며 출하 판정 권한이 없다.

### 결함 발견 시
- 결함 수리: 작성자가 수정 → V1(또는 V2)에 **그 항목만** 재확인 요청. 전체 QC를 다시 돌리지 않는다.
- 같은 결함이 재확인에서도 잔존하면 Phase 6로 회귀(구조 문제)

### 출하 판정 (V3.1 — OR 게이트 선택 기준 명시)

```
✅ 합격 — 7-5 합격선(V1·V2 총점 ≥95 · Critical·High 0 · 4단 QC 전항 O · 사용자 여정 KPI) 충족 → Phase 8 출하
❌ 불합격 — 결함 잔존 → 회귀 깊이 결정 표 적용
```

| 결함 유형 | 회귀 위치 | 판정 기준 |
|--------|----------|----------|
