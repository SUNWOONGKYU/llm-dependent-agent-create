## Phase 2.5 ★V3.5 R15 신설 — 도메인 심층 리서치 (Deep Domain Research)

> ★V3.25 — **발굴 경로 A(지정 원자재)면 이 Phase를 생략한다.** 원자재 자체가 도메인 표본이다. 경로 B만 수행.

> **PO 지적 회고 (2026-05-29)**: "AI가 어느 정도 상황 파악한 다음에 지구상에 있는 모든 관련된 것들을 조사하는 그 프로세스가 있어야만이 제대로 된 수준 높은 에이전트가 나온다." → Phase 3은 "부품 발굴"이라 도메인 자체 광역 조사가 빠져 있었음.

**왜 필요한가**: Phase 1·2까지는 "PO 의도 파악". Phase 3은 "부품 단위 발굴". 그 사이에 **"이 분야 자체에 어떤 깊이가 표준인가"** 광역 리서치가 빠지면 *PO 의도는 잘 파악했는데 도메인 표면 위에서 조립*하게 된다. 표면적 에이전트로 끝남.

### 2.5-1. 키워드 망 작성

Phase 1 기획안 + Phase 2 MBO에서 도출된 도메인·문제·트리거 키워드를 망 형태로 정리. 영문·한국어 양쪽.
- 핵심 키워드: 3~5개 (도메인·작업)
- 보조 키워드: 5~10개 (관련 도구·기술·용어)
- 부정 키워드: 2~3개 (혼동 위험 — 검색 제외용)

### 2.5-2. 4개 트랙 병렬 조사 (★핵심)

| 트랙 | 조사 대상 | 출처 |
|------|---------|------|
| **① 기존 솔루션·경쟁** | 같은 문제 푸는 에이전트·서비스·OSS — 차별점 후보의 근거 | GitHub `awesome-*`, ProductHunt, 스킬스토어, Google 검색 |
| **② 학술·표준** | 분야의 정설·가이드라인·규제 (의료·법률·금융 등 규제 도메인은 필수) | Google Scholar, arXiv, 표준 문서 (ISO·NIST·GDPR·의료 가이드) |
| **③ 사용자 워크플로우** | 실제 사용자가 어떤 흐름으로 일하는가 — 빠진 단계가 곧 차별점 | Reddit, Stack Overflow, 도메인 커뮤니티, 사용자 블로그·후기 |
| **④ 실패 사례·교훈** | 같은 문제 풀려다 실패한 사례 — 우리 함정 회피 | 사후 분석(post-mortem) 글, "X failed because" 검색, 회의록·이슈 트래커 |

각 트랙은 **WebSearch·WebFetch·Subagent 도구 위탁** 가능. 병렬 처리 권장.

### 2.5-4. PO 게이트 (1회)

요약서를 PO에게 제시 → PO 확인 한 줄:
- ✅ "이 정도 깊이면 OK" → Phase 3 진입
- 🔁 "트랙 N번 더 깊이" → 2.5-2 해당 트랙만 재실행
- ❌ "방향 잘못됨 — Phase 2 MBO 재정의" → Phase 2 회귀

⛔ **PO 게이트 통과 없이 Phase 3 진입 금지.**

### 2.5-5. 규모별 강도

| 규모 | 트랙별 스캔 건수 | 권장 도구 |
|---|:---:|---|

| **L (복잡)** | 각 10건+ (총 40건+) | 별도 Subagent 위탁 (트랙당 1명, L만) + 작성자 종합 (원문은 `research_raw/`에 보존) |

### 2.5-6. 종합 주체 (★V3.23)

L 규모는 트랙별로 Subagent 띄울 때 제조 의도 비전달. 리서치 결과 **종합은 작성자**가 한다. 여기서 V1을 부르지 않는다 — 원문을 `_개발자료/_design/research_raw/`에 보존해 Phase 7 검증자가 필요 시 대조한다.

### 2.5-8. 외부 도메인 리서치 ≠ Phase 3 부품 발굴

| 항목 | Phase 2.5 | Phase 3 |
|---|---|---|
| 단위 | 도메인·솔루션·논문 | 부품(함수·코드 블록·체크리스트) |
| 목적 | "어떤 깊이가 표준인가" 광역 인식 | "재료 어디서 가져올까" 구체 발굴 |
| 결과 | 1장 요약서 | BOM 5분류 표 |

두 Phase는 같은 도구(WebSearch·WebFetch·Glob)를 쓰지만 *시야 깊이가 다르다*. Phase 2.5가 멀리·넓게, Phase 3가 가까이·구체적으로.
