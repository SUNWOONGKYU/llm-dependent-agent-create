# 설계 산출물 규격 — 목표서 삽입 절 · plan · 관계도/흐름도 · BOM · 설계 검증 · 갱신 규정

> 에신 V4 docs 모듈 — Phase 2 · 4 · 5 · 6 마감 에서 읽는다. 목적: 설계 파일 5종의 양식과 "구현이 달라지면 아키텍처 파일을 고친다"는 규정
> 문서 순서: Phase 1 설계서 초안+관계도·흐름도 → Phase 2 목표서 승인 → Phase 3·4 부품 발굴·검증(BOM) → **Phase 5 설계서 확정+설계 검증** → 6 조립 → 7 출하 검증 → 8 출하 → 9 운영. **부품(BOM)이 정해져야 설계서(plan.md)가 완성된다** — Phase 4 없이 Phase 5로 못 간다. 설계서(plan.md) = *어떻게 만드는가*, 목표서(mbo 목표서) = *무엇을 왜 + 승인* — 역할이 다르고 이름도 바꾸지 않는다.
> 출처: 에신 V3.27 본문(2026-09-17)을 절 단위로 옮긴 것. 절차·표는 그대로, 판정 권한은 SKILL.md §3 Phase 표가 단일 출처.

## Phase 2. 목표 정의 — mbo-천상 호출 + 승인 게이트 (★V3.22 — 양식 복제 폐지, 스킬 호출로 전환)

**목표서 양식·승인·MBO 파일 저장·결과 보고는 `mbo-천상` 스킬이 단일 출처다.** 에신은 양식을 베끼지 않고 `mbo-천상`을 호출해 그 절차를 그대로 탄다. 에신이 보태는 것은 딱 하나 — 에이전트 고유 「제조 대상 — 7대 구성요소 + 메타」 절을 목표서에 **삽입**하는 것뿐이다.

이 단계에서 에이전트 **규모(S/M/L)를 확정**한다. 배치/포털 모드는 자동으로 L (배포형·다수 에이전트·호스팅) 판정.

### 호출 규격 (에신 → mbo-천상)

| mbo-천상 단계 | 에신에서의 처리 |
|---|---|
| PHASE 1 Step 1 맥락 분석 · Step 2 스무고개 | **건너뜀** — 에신 Phase 1(10라운드 + α 문답)이 이미 수행. Phase 1 산출물(기획안·출력 대상 명세)을 mbo-천상 입력으로 넘긴다 |
| Step 3 AS-IS 조사 | 수행 — 현재 사람이 하는 방식(수작업)을 조사해 「현재 vs 목표」의 AS-IS 칸을 채운다 |
| Step 4 MBO 목표서 작성 | mbo-천상 양식(최상위 목표·현재 vs 목표·KPI·산출물·완료·검증 기준[공개본 명칭 「목표 달성 평가·검증 기준」+「자가수정 한도」]·실행 계획·리스크) **그대로** + 「최상위 목표」 바로 아래에 아래 **삽입 절**을 넣는다. 제목은 `MBO 목표서 — 에이전트 제조: {에이전트명}` |
| Step 5 PO 승인 | mbo-천상 게이트 그대로. ⛔ 승인 없이 Phase 2.5 이후 진행 절대 금지. 수정 요청 시 재제시 |
| PHASE 2 MBO 파일 저장(공개본 명칭 「목표서 파일 저장」) | **에신 작업 폴더**(Phase 0에서 지정) 루트에 `YYYY_MM_DD__HH.MM_mbo-천상_{에이전트명}.md` 저장 — 컴팩션·세션 교체 대비 |
| PHASE 2 자율 실행 | 에신 Phase 2.5 → 9 가 곧 실행 계획. 실행 계획 표의 Task = 에신 Phase 목록 |
| PHASE 3 결과 보고 | 에신 Phase 8 출하 보고서 직후 `/mbo-천상 report`(공개 설치본 `/mbo report`) 로 KPI 실측·산출물·검증 대조 → 저장한 MBO 파일 하단에 덧붙임. 자가수정 게이트(미달 시 Phase 7 QC 또는 Phase 2 재승인 회귀)도 mbo-천상 규정 따름 |

KPI 작성 시 에신 고유 제약(mbo-천상 양식 위에 얹음):
- 반드시 **사용자 여정 KPI 1개 이상** — "파일 생성"은 데이터 KPI일 뿐
- 비용/보안/컴플라이언스 KPI 각 1개 이상 권장 (V3.0)
- 실행 계획 표에는 에신 Phase 2.5·3·4·5·6·7·8·9 를 Task로 나열 (규모별 생략 Phase는 "생략 — 사유" 명시)

## Phase 4. 분해·검증 — "정밀 선별" ★공장의 심장

> ★V3.12 부품을 채택하면 **회귀 테스트 승계표**(원본이 보장하던 행동 → 원본 테스트 → 우리 대응 테스트 → 실호출 증거)를 함께 만든다. 코드만 가져오고 검증을 두고 오면 안 된다.

**발굴물을 통째로 신뢰하지 않는다.** 작업대에 올려 부품 단위로 검증하고, 결함은 걸러낸 뒤 검증된 부품만 선별한다.

### 4-1. 입고 검사 — 후보별 5대 KPI 채점

| 지표 | 합격선 | 측정 |
|------|--------|------|
| **명료성** | Read 1회 5분 내 이해 | 사용 시점·절차·예시 존재 |
| **운용 충돌** | **0건 — 타협 불가** | 한국어 출력·보안 가드·SAL/MBO 자동감지 위반 0 |
| **최신성** | 6개월 이내 업데이트 | 커밋·릴리스·작성 날짜 |
| **의존성 부담** | npm/pip 추가 1개 이하 또는 검증된 메이저 OSS | 의존성 트리 |
| **검증 가능성** | 결과물 객관 검증 가능 | V1 투입 가능 여부 |

5개 중 4개 미만 → 후보 폐기 또는 fork. **"운용 충돌 0건"은 어떤 경우에도 타협 불가.**

### 4-2. 부품 단위 분해

후보를 통째로 채택하지 않는다. **함수·모듈·프롬프트 블록·설정 단위로 쪼개** 각각을 분류한다.

### 4-3. 안전성 진단 (주작 방식) → 걸러내기

발굴물을 위험도·안전성 관점에서 감사 (주작-sal-da 방식). 다음은 발견 즉시 제거:
- `eval()`·`exec()`·검증 없는 shell 직접 실행
- 하드코딩된 시크릿·API 키·절대경로
- PO 보안 가드 위반 (외부 드라이브 무단 접근, `.env` 노출 등)
- deprecated 라이브러리·API 의존
- 영어 강제 출력 등 한국어 운용 규칙 위반
- `href` 없는 버튼·죽은 링크 (UI 에이전트의 경우)
- 1년 이상 미유지보수 코드

### 4-5. 이중 분류 규칙 (V3.1 신설 — 🔵 ∩ 🏭 교집합 처리)

한 부품이 여러 분류에 동시 해당할 수 있다. 다음 우선순위 규칙으로 단일 레이블 부여:

```
🟢/🟡  >  🔵  >  🏭  >  🔴
```

**판정 절차**:
1. **출처 우선** — 발굴물에서 가져온 것이면 🟢/🟡 (재단 여부로 갈림). 출처가 외부면 무조건 🟢/🟡 분류가 1순위.
2. **범위 우선** — 자체 제작이지만 N 에이전트가 공유한다면 🔵 (배치/포털 모드만). 단일 모드에서는 🔵 불가.
3. **신규 제작 단독 사용** — 🏭
4. **결함** — 🔴 (다른 분류와 동시 적용 불가, 항상 거부)

**예시**:
- 비용 가드 코드를 자체 제작했고 93 에이전트가 모두 쓴다 → **🔵** (🏭 아님)
- 비용 가드를 PyPI 라이브러리로 가져와 그대로 적용 → **🟢** (🔵 아님)
- 단일 에이전트 전용 OCR 코드를 자체 제작 → **🏭** (🔵 아님)
- 단일 에이전트가 OSS OCR 라이브러리 가져와 한국어 폰트만 추가 → **🟡** (🏭 아님)

BOM 작성자는 한 부품을 두 분류에 동시 기입하지 않는다 — 단일 레이블만.

🔵 공통부 부품의 예 (제작자 선행 프로젝트 93개 + claude-news-agent 사례):
- 비용 가드 3중 (per_run / per_user_monthly / monthly)
- 세션 HMAC + role 기반 권한 + 회원가입 승인
- 공급자 공통 tool round-trip (Anthropic/OpenAI/Gemini/xAI 중 **채택한 것**만 실호출 — ★V3.12)
- **LLM 폴백 체인 모듈 ★V3.5 신설 표준 자산** — 단일 키 401/402/429/credit 한도 시 자동 폴백 (예: `llm_providers.py` Claude→Gemini→GPT→Grok). (회고 사유: claude-news-agent 첫 실행 시 ANTHROPIC_API_KEY 401로 전체 멈춤 — 폴백 추가 후 정상 작동) ⚠️ **이 API-키 폴백 체인은 웹사이트형(포털·서버) 런타임의 표준이다.** 데스크톱형(PO 본인용 로컬)은 위 💳 원칙대로 **`claude` CLI(구독) → `codex` CLI 2차 검증**을 표준으로 하고 API-키 폴백 체인은 *배포용일 때만* 넣는다. (제작·검증은 웹사이트형/데스크톱형 불문 항상 구독 — API 금지.)
- 면책·디스클레이머 정책
- 첨부 처리 (Vercel 4.5MB → Storage signed URL 우회)
- 사용 로그·피드백·관리자 콘솔

배치/포털 모드는 🔵가 반드시 채워진다 — 비어 있다면 Phase 1c를 다시 점검한다.

**단일 모드 예외 (V3.5)**: 단일 모드는 원래 🔵 불가지만 **LLM 폴백 체인 모듈**(웹사이트형) 또는 **CLI 호출 헬퍼 `_sub_env()`+claude·codex CLI**(데스크톱형)만은 단일 모드에서도 🏭(자체 제작)로 분류하여 반드시 포함한다. 단일 LLM 의존은 첫 출하 직후 멈춤 사고를 부른다.

### ★ 자기완결 원칙 폐지 (★V3.22 — 두 공장 동기화, V4.4 에서도 유지)

V3.4~V3.21의 "자기완결 원칙"(외부 스킬 호출 금지·외부 AI 호출 금지·내장 Subagent만 검증)은 **폐지**한다. 대신:
1. **핵심 절차는 계속 본문에 내장** — Phase 5 설계 검증 체크리스트, Phase 7 QC 4단은 그대로 이 문서 안에 있다. `/review-evaluate`·`/pro-persona-debate`·`/주작-sal-da` 호출 의무는 여전히 없다.

Phase 7 V1 「사실 정확성」이 SVG 도 대조하되, **설계 자체의 적합성은 Phase 5 에서 이미 끝났으므로** Phase 7 은 "구현 ↔ 이 시점의 SVG/plan" 대조에 집중한다.
