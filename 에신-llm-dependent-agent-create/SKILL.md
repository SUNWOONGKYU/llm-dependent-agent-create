# 에신 — LLM 의존형 에이전트 제조 공장 (V4)

> **이 파일은 지휘 문서다.** 순서·분기·산출물·게이트만 적는다. 절차의 «어떻게»는 `docs/`, 복사할 파일은 `templates/`, 넘어갈 조건은 `checklists/` 에 있다. 한 Phase 를 할 때는 §3 표에서 그 행을 찾고 거기 적힌 파일만 연다.
> 도식: `_design/에신_V4_architecture.svg` (좌 관계도 · 우 흐름도). 이 파일과 도식이 어긋나면 도식이 틀린 것 — 같이 고친다.

## §0. 이 스킬을 읽는 법 (30초)

```
에신-llm-dependent-agent-create/
├─ SKILL.md            ← 지금 이 파일. §3 Phase 표가 전부다
├─ docs/               읽는 것 — 00 7요소 · 01 GUI 표준구성 · 05 요구발굴 12개 요구 항목 정의서 · 10 시동·발굴 · 15 리서치 · 20 설계 규격 · 30 조립 공통 · 31 GUI 트랙 · 32 비GUI/웹 · 40 시험 · 50 검증 · 60 출하·운영
├─ templates/          복사해서 채우는 것 — 실행부 5(store·llm·guard·engine·run _skeleton.py) · GUI 3(gui_skeleton/index.html · ui_skeleton.py · smoke_ui.py) · 시작.bat · CLAUDE.md · uicontract.py · setup_helper.py · 출하_정리.py · test_gates.py · verify_windows_adapter.ps1 · V1_지시서_설계검증(Phase 5) · V1_지시서(Phase 7) · V2_지시서(Phase 7) · 양식/(plan·bom·대조표)
├─ checklists/         넘어갈 조건 — phase_gates · phase5_설계검증 · gui_고정표 · v1_v2_대조표
├─ _design/                      이 스킬의 관계도·흐름도
└─ CHANGELOG.md        이력
```

- 학생·처음 쓰는 사람: §1 원칙 → §3 표를 위에서부터. 각 행의 「읽을 것/복사할 것」만 열면 된다. 다른 에이전트 원본을 찾을 필요 없다 — 필요한 구성은 전부 여기 옮겨져 있다.
- 산출물 = 에이전트 폴더(§6). 완성도 높은 실물 에이전트의 구조를 그대로 따른다.
- 에이전트 제작 대상은 **웹사이트형**(서버에 올려 다수가 사용)·**데스크톱형**(로컬 PC 설치, 혼자 쓰거나 여러 사람이 공용 사용) 두 가지로 한정한다. 어느 쪽이든 완성된 에이전트 본체는 **실행부**(LLM 호출·판단·도구 실행)·**화면부**(사람이 보는 창과 접속 주소)·**공통부**(로그인·기록·결제·LLM 대체 경로) 세 부분을 전부 갖춘다 — 규모(S/M/L)는 각 부의 크기만 정한다.

## §1. 원칙 9 (어기면 출하 무효)

1. **역할 고정** — 나는 제조자다. 에이전트가 할 일(문서·논문·판정)을 대신 하지 않는다. 시운전은 1회, 제품 내부 지표(점수·라운드)를 PO 에게 중계하지 않는다.
2. **자기검증 금지** — 만든 사람이 자기 결과를 통과시키지 않는다. 검증자는 **Phase 5(설계 검증)·Phase 7(출하 검증) 두 곳에서만** 부른다(각 1회, 중간 라운드 없음). 두 Phase 의 V1 은 같은 세션이 아니어야 한다.
3. **뼈대 복제** — 데스크톱형 GUI 는 `templates/gui_skeleton/index.html`·`ui_skeleton.py` 를 복사해 `{{ }}` 만 채운다. 블록 이동·삭제·접기 변경 금지. 자리 표시 어휘(접수·작업·사건)는 도메인 사람의 말로 전부 바꾼다.
4. **LLM = CLI 두 종, 자리 세 개** — 작업·1차 검증 = Claude Code CLI(두 자리, 별도 호출), 2차 검증 = Codex CLI. 다른 CLI 를 끼워 넣지 않는다. 제작·검증·로컬 런타임은 구독, API 키는 웹사이트형 서버에만.
5. **미확인 ≠ 통과, 정의됨 ≠ 호출됨** — 설치 확인은 작동 확인이 아니다(칩 4값). 문서에 «구현했다»고 적은 함수는 코드에 있고 다른 곳에서 불려야 한다(시험이 잡는다). LLM 「1차·2차 검증」은 칩이 아니라 `verify_1st`·`verify_2nd` 호출이 있어야 검증이다.
6. **아키텍처 파일(설계서 + 관계도·흐름도)은 구현과 같아야 출하** — Phase 5 에서 부품이 확정된 뒤 설계서를 확정하고 검증받는다. 구현이 설계와 달라지는 순간 SVG·plan 을 고치고, Phase 6 마감에 화면 단계 ↔ 흐름도 1:1 을 대조한다.
7. **상태를 지우는 경로는 확인 + 백업** — 초기화 전 백업, 단계마다 스냅샷. 검증자 소환 전에도 스냅샷.
8. **외부 의존은 정확히 2개** — `mbo-천상`(목표·승인·보고, 없으면 자동 설치) · `Codex`(V2, 없으면 Opus 5 Teammate 폴백). 그 외 스킬은 있으면 쓰고 없으면 본문 폴백.
9. **PO 게이트 2개만** — Phase 2 목표서 승인 · Phase 2.5 리서치 깊이(경로 B). 나머지는 자율. 결함·안건은 한 번에 하나씩.

## §5. 합격 판정 — Phase 5 설계 검증 + Phase 7 출하 검증 (7-5)

### Phase 5 — 설계 검증 (이진 체크리스트 11항목, 점수 없음, ★V4.8 — 12항목→11항목 개정)

V1 은 plan.md·관계도/흐름도 SVG·bom.md + 승인된 목표서(항목 3 대조용) **문서만** 읽고 아래 11항목을 O(소거됨)/X(잔존)로 판정한다. 코드 실행 없음. 통합 항목(1·2·10)은 하위 확인을 각각 기록하고 하나라도 X 면 그 항목 X. ★ 표시(7~10)는 안전·부품 항목 — 반려 보고 시 먼저 제시.

[구조]
1. 7대 구성요소가 plan.md·관계도·BOM 세 곳에 모두 대응하는가 (하위: plan 명시·관계도 노드·BOM 매핑)
2. 흐름도가 시작→종료까지 끊김 없이 연결되고, 관계도에 고립된(연결 안 된) 구성요소가 없는가

[목표·요구]
3. plan.md 핵심값이 승인된 목표서(mbo)와 일치하는가
4. 요구 항목마다 plan.md 어느 절에 반영됐는지 대응되고, 빈칸·템플릿 문구가 없는가
5. 완료 기준이 측정 가능한 값(수치·비율·예/아니오 중 하나)으로 적혀 있는가
6. plan.md 에 적힌 화면 구성 방향이 사용자층·구동방식과 모순되지 않는가(비GUI 트랙은 "명령 방식(비GUI)", GUI 트랙은 "고정표 그대로" 표기로 충분 — 해당 없으면 자동 O)

[안전] ★
7. 안전 체계 값이 실제 수치·정책으로 채워졌는가(비용·종료·보안·도메인 가드)
8. 도구마다 허용 동작(읽기·쓰기·삭제·외부 전송)이 정해졌고, 되돌릴 수 없는 작업 앞에 사람 승인 지점이 있는가(읽기 전용뿐이면 자동 O)
9. 실패 모드가 구체적으로 정의됐는가 — 도구 실패·LLM 실패(폴백)·프롬프트 인젝션 3종(외부 입력 없으면 인젝션 하위 자동 O)

[부품] ★
10. 버린(🔴) 부품이 채택 목록(🟢/🟡/🏭/🔵)에 다시 섞이지 않았고(버린 기록 보존은 정상), 라이선스가 금지 목록에 해당하지 않는가(카피레프트는 코드 복사 금지·구조 참고만 조건부 O)

[문서]
11. 관계도·흐름도 SVG 가 plan.md 최신 버전과 절 번호 1:1 로 대응하는가(설계 내부 일관성만, Phase 6 마감에 재확정)

**합격 = 11항목 전항 O.** X 가 있으면 작성자가 그 항목(통합 항목은 X 난 하위만)만 고쳐 V1 에게 **그 항목만** 「소거됨/잔존」 재확인 요청(재채점·전항 재검토 없음). 위 11항목은 요약이며 **단일 출처는 `docs/20` §5-2**(항목별 판정 방법·금지 라이선스 표 포함). 첫 실전 1건 시범 적용 후 판정 문구 보정 예정.

### Phase 7 — 출하 검증 (5축 100점 + 4단 QC, 점수 있음)

설계 적합성은 Phase 5 에서 이미 검증했으므로, Phase 7 은 **「구현이 설계대로인가 + 실제로 도는가」**에 집중한다. V1·V2 는 **5축 100점**(사실 정확성 20 · 용어 일관성 15 · 규칙 준수 20 · 실용성 20 · 사양 충족률 25 — 「구조 완성도」축은 Phase 5 설계 검증으로 이관되어 폐지)을 매기고, **4단 QC**(7-1 정적 · 7-2 동적 · 7-3 클릭/실기동 · 7-4 가드 시뮬)를 O/X 로 따로 판정한다. ★V4.11 — **7-4b 요구 값 강제 대조**를 추가로 O/X 판정한다: Phase 5 항목 7·8 은 "값이 설계서에 적혀 있는가"만 봤다(문서만, 코드 미실행) — 7-4b 는 그 값을 **코드가 실제로 강제하는가**를 대응표(요구 값/설계서 위치/코드 위치/강제 방식/증명 시험/한계)로 확인한다. 대응표 누락·코드 불일치·증명 시험 부재·숨긴 한계는 Critical.

**합격 = 총점 ≥ 95 AND Critical·High 0 AND 4단 전항 O AND 7-4b 요구 값 대응표 완결 O AND (GUI) 고정표 X 0 AND 사용자 여정 KPI O.**
불합격 → 작성자 수정 → 검증자에게 **그 항목만** 「소거됨/잔존」 → 잔존이면 Phase 6 회귀. V2 는 L 만, `|V1−V2| > 3` 이면 V2 결함 수정 후 항목 재확인. Medium·Low 는 Phase 9 백로그. 제품 내부 자가 점검 점수는 출하 판정 권한이 없다. 상세 `docs/50`.
